## 🤔 一、传统模式：服务端渲染

早些年写网站，前端和后端是"绑在一起"的。你在浏览器输入 `https://shop.com/products`，服务器收到请求后，现场查数据库、把数据塞进 HTML 模板、生成一整页 HTML 返回给浏览器。

```text
浏览器 → GET /products → 服务器（查DB + 渲染模板）→ 完整HTML → 浏览器渲染
```

这种模式下，前端代码（HTML/CSS/JS）是嵌在后端项目里的，比如 JSP、PHP、Thymeleaf 模板。前端工程师想改个按钮样式，得在后端项目里找模板文件；后端工程师想改个接口，可能影响前端页面渲染。两个人互相"踩脚"。

而且每次跳转页面，浏览器都要重新请求服务器，白屏一下再渲染——体验很差。

---

## 💡 二、前后端分离：各干各的

前后端分离的思路很简单：**前端和后端完全拆成两个独立项目**，通过 HTTP API 通信。

```text
前端项目（Vue）          后端项目（Spring Boot / Express / Django）
┌──────────────┐          ┌──────────────────────┐
│ 负责 UI 渲染  │  AJAX    │ 负责数据处理          │
│ 负责用户交互  │ ──────→ │ 负责业务逻辑          │
│ 跑在浏览器里  │ ←────── │ 提供 JSON API        │
└──────────────┘  HTTP    └──────────────────────┘
```

前端不再关心数据怎么存在数据库里，只关心"我要从哪个 URL 拿数据"；后端不再关心页面按钮长什么样，只关心"收到请求后返回什么 JSON"。

两个项目可以：
- 用不同语言（前端 TypeScript，后端 Java/Python/Go）
- 由不同人开发
- 独立部署、独立扩容

## 🔑 三、HTTP 协议：前后端怎么"说话"？

前后端分离后，前端和后端靠 **HTTP 协议** 通信。理解 HTTP 是做服务端通信的基础。

### 3.1 一个 HTTP 请求长什么样

```http
GET /api/products HTTP/1.1
Host: shop.com
Authorization: Bearer eyJhbGciOiJIUzI1NiJ...
Content-Type: application/json
```

- **方法（Method）**：GET（拿数据）、POST（新增）、PUT（修改）、DELETE（删除）
- **URL**：要访问的资源地址
- **请求头（Headers）**：附加信息，比如认证 token、内容类型
- **请求体（Body）**：POST/PUT 时携带的数据（通常是 JSON）

### 3.2 一个 HTTP 响应长什么样

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "code": 0,
  "data": [
    { "id": 1, "name": "iPhone 15", "price": 5999 }
  ]
}
```

- **状态码（Status Code）**：200 成功、404 找不到资源、500 服务器内部错误
- **响应体（Body）**：后端返回的数据，前端拿到后渲染到页面上

### 3.3 常见状态码速查

| 状态码 | 含义 | 场景 |
|---|---|---|
| 200 | 成功 | 正常拿到数据 |
| 201 | 已创建 | POST 新增成功 |
| 400 | 请求错误 | 参数格式不对 |
| 401 | 未认证 | 没登录 / token 过期 |
| 404 | 找不到 | URL 写错 / 资源不存在 |
| 500 | 服务器错误 | 后端代码崩了 |

## 🛠 四、API：前后端的"约定"

**API（Application Programming Interface）** 就是前后端之间的一套约定：哪个 URL 做什么事、发什么参数、返回什么格式。

### 4.1 RESTful 风格（最常见）

RESTful 是一种设计 API 的约定，核心思想：**URL 表示资源，HTTP 方法表示动作**。

```text
GET    /api/products        → 获取产品列表
GET    /api/products/1      → 获取 ID=1 的产品详情
POST   /api/products        → 新增一个产品
PUT    /api/products/1      → 修改 ID=1 的产品
DELETE /api/products/1      → 删除 ID=1 的产品
```

### 4.2 请求和响应都是 JSON

前端发请求：

```json
// POST /api/products 的请求体
{
  "name": "iPhone 15",
  "price": 5999
}
```

后端返回响应：

```json
// 响应体
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 42,
    "name": "iPhone 15",
    "price": 5999
  }
}
```

前端拿到 `data` 里的数据，用 `ref` 存起来，渲染到页面上——这就是 Vue 里"服务端通信"的本质。

## ⚠️ 五、前后端分离的常见坑

### 坑 1：跨域问题（CORS）

前端跑在 `http://localhost:5173`，后端跑在 `http://localhost:3000`，浏览器会拦截前端的请求——这叫**跨域**。

```text
浏览器报错：
Access to XMLHttpRequest at 'http://localhost:3000/api/products'
from origin 'http://localhost:5173' has been blocked by CORS policy
```

**解决办法**：后端加 CORS 头，或者开发阶段用 Vite 的代理配置：

```js
// vite.config.js
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
      }
    }
  }
})
```

### 坑 2：接口还没写好，前端怎么开发？

实际工作中，后端 API 经常比前端晚好几天。前端可以：
- 和后端先约定好 API 文档（URL、参数、返回格式）
- 用 **Mock 数据** 模拟接口返回（后面章节会讲）

### 坑 3：状态码理解错误

很多初学者以为"能拿到数据就是 200"。实际上：
- 404 也可能是前端 URL 写错了
- 401 说明登录态失效，需要跳转到登录页
- 500 是后端崩了，前端能做的只有展示"服务器繁忙，请稍后重试"

## 🧠 本节小结

- **两种架构模式**：服务端渲染把页面和数据揉在后端模板里，前后端分离则让前端只写 UI、后端只吐 JSON，两者靠 HTTP API 通信
- **HTTP 请求四要素**：方法（GET/POST/PUT/DELETE）+ URL + 请求头 + 请求体；响应重点看状态码和响应体
- **常见状态码**：200 成功、201 已创建、401 未认证、404 找不到、500 服务器错误——看到报错先对号入座
- **API 约定**：RESTful 风格用「URL 表示资源、方法表示动作」，前端最常打交道的是 JSON 请求与响应
- **Vue 的位置**：前端拿到响应里的 `data`，用 `ref` 存起来再渲染到页面——这就是服务端通信的本质
