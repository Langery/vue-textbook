很多新手以为"组件能跑就行"，于是写出一个"万能组件"：既管展示又管数据请求，还得兼职做表单校验，需求一多就在模板里塞满 `v-if` 分支。结果呢？产品提了个小改动，你战战兢兢改了三天，还连带修出两个新 Bug——因为牵一发动全身。本节开始聊组件设计原则：好的组件不是功能多，而是**责任清晰、接口稳定**，第一条原则就叫"单一职责"。

## 🤔 一、组件设计的三个原则（总览）

前面我们学会了**组件是什么**——独立的 UI 积木。但「把代码拆进组件」和「把组件设计好」是两码事。

同样是拆组件：

- **烂拆法**：拆是拆了，但组件之间相互依赖、改一个要动三个、复用性为零
- **好拆法**：每个组件独立、清晰、灵活，拿来就能用，改也只要改一处

区别在哪里？就在三个设计原则上：

| 原则 | 解决什么问题 | 一句话概括 |
|---|---|---|
| **单一职责** | 组件"做什么" | 一个组件只做一件事 |
| **开闭原则** | 组件"怎么变" | 对扩展开放，对修改关闭 |
| **低耦合** | 组件之间"怎么配合" | 组件之间尽量独立 |

> 💬 **老师备注**：这 3 个原则不是 Vue 独有的，它们源自软件工程的经典设计原则（SOLID），但在 Vue 组件化开发中**特别实用**。背下来不费劲，但**用出来需要反复练**。本节先学前两个，3.6 节学完低耦合并做综合重构练习。

## 💡 二、原则 1：单一职责（Single Responsibility）

### 定义

> **一个组件应该只做一件事，并且把这件事做好。**

### 反例：「神组件」

来看看一个"什么都能干"的组件长啥样：

```text
UserDashboard.vue （❌ 神组件 —— 管太多）
├── 用户头像和资料（用户信息）
├── 最近订单列表（订单）
├── 消息通知面板（通知）
├── 快捷操作按钮（操作）
└── 数据统计图表（统计）
```

<img src="../00-公共资源/图/03-组件化思想/图3-2.svg" alt="神组件 vs 单一职责组件的对比">

这个组件管了 **5 种完全不同的业务**。后果：

- **难维护**：改订单列表，可能不小心改到通知面板的逻辑
- **难复用**：我想在另一个页面单独用"消息通知面板"？对不起，它跟用户头像焊死了
- **改一个功能，全局都得测**：加一个统计图表，全组件都要回归测试

### 正例：拆成单一职责组件

```text
UserDashboard.vue （✅ 只做"布局"）
├── <UserProfile />       ← 只管用户信息
├── <RecentOrders />      ← 只管订单列表
├── <NotificationPanel /> ← 只管消息通知
├── <QuickActions />      ← 只管快捷操作
└── <StatsChart />        ← 只管统计图表
```

<img src="../00-公共资源/图/03-组件化思想/图3-2.svg" alt="神组件 vs 单一职责组件的对比">

> 💬 **老师备注**：判断一个组件是否"单一职责"，有个很简单的测试——**你能不能用一句「这个组件负责...」来描述它？** 如果这句话里出现「和」，比如"负责用户信息**和**订单列表**和**通知"，那它大概率职责不单一。

### 单一职责的粒度怎么把握？

不是越细越好。一个参考粒度标准：

| 粒度级别 | 例子 | 什么时候拆 |
|---|---|---|
| **原子级** | `<BaseButton>`、`<BaseInput>` | 整个项目多处复用 |
| **区块级** | `<ProductCard>`、`<CommentItem>` | 当前页面/模块内复用 |
| **页面级** | `<HomePage>`、`<LoginPage>` | 一个路由对应一个页面组件 |

## 💡 三、原则 2：开闭原则（Open-Closed Principle）

### 定义

> **对扩展开放：可以通过 Props 传入不同数据来改变行为。**
> **对修改关闭：不要为了某种定制需求，跑去改组件本身的源代码。**

### 反例：写死的组件

```
<!-- ❌ Badge.vue：写死的组件 -->
<script setup>
const text = '新品'
const color = 'red'
</script>

<template>
  <span :style="{ background: color }">{{ text }}</span>
</template>
```

**问题**：每次要用不同文字或颜色，就得复制一份代码，改 `text` 和 `color`。一周后你可能有了 `BadgeNew.vue`、`BadgeHot.vue`、`BadgeSale.vue`⋯⋯

### 正例：通过 Props 开放的组件

```vue
<!-- ✅ Badge.vue：开放扩展的组件 -->
<script setup>
// 通过 defineProps 声明组件能接收的参数
const props = defineProps({
  text: {
    type: String,
    required: true
  },
  color: {
    type: String,
    default: '#e53e3e'  // 默认红色
  },
  size: {
    type: String,
    default: 'medium',
    validator: (val) => ['small', 'medium', 'large'].includes(val)
  }
})
</script>

<template>
  <span class="badge" :class="`badge--${size}`" :style="{ background: color }">
    {{ text }}
  </span>
</template>

<style scoped>
.badge {
  display: inline-block;
  padding: 2px 8px;
  border-radius: 4px;
  color: #fff;
  font-size: 12px;
}
.badge--small  { padding: 1px 6px; font-size: 10px; }
.badge--large  { padding: 4px 12px; font-size: 14px; }
</style>
```

**使用方式**：

```vue
<template>
  <Badge text="新品" color="#e53e3e" size="small" />
  <Badge text="热卖" color="#dd6b20" size="medium" />
  <Badge text="限时" color="#3182ce" size="large" />
</template>
```

**一个组件，三种用法**——这就是"对扩展开放"的力量。

> 💬 **老师备注**：开闭原则的核心是——**把"不变的东西"留在组件内部，把"可变的东西"通过 Props 暴露出去**。怎么判断什么东西"可变"？看业务需求：文字能不能换？颜色能不能改？尺寸能不能调？

## ⚠️ 四、常见陷阱

### 陷阱 1：把所有东西都拆成组件

不是拆得越细越好。如果一个组件只在一个地方用、逻辑非常简单、没有复用可能——**先放一起，等有了复用需求再拆**。（3.7 节会深入讲"拆多细合适"）

### 陷阱 2：Props 传一个巨大对象

```
<!-- ❌ 传一个几十个字段的大对象 -->
<CourseCard :course="course" />
```

如果 CourseCard 只用到了 `course` 里的 3 个字段，那它跟整个 `course` 对象强绑定——将来 `course` 改字段名，CourseCard 也要改。

```vue
<!-- ✅ 只传组件真正需要的 -->
<CourseCard
  :name="course.name"
  :teacher="course.teacher"
  :price="course.price"
/>
```

### 陷阱 3：子组件里直接改 Props

```
<script setup>
const props = defineProps({ count: Number })
props.count++ // ❌ Vue 会报警告：Props 是只读的！
</script>
```

如果需要"改"，应该通过 emit 通知父组件去改（或者用 `v-model`），第 4 章会讲。

## 🧠 本节小结

- **组件设计三原则**：单一职责、开闭原则、低耦合——本节讲前两条
- **原则 1 单一职责**：一个组件只做一件事；「神组件」管太多 = 改一个需求牵动全身
- **把握粒度**：功能是否内聚、是否易理解，而不是机械地"越小越好"
- **原则 2 开闭原则**：对扩展开放、对修改关闭——用 Props 把差异暴露给外部，而不是把组件写死
- **常见翻车**：什么都拆成组件、Props 传巨大对象、子组件直接改 Props
