## 🧠 思维导图

```text
3.2 组件文件怎么组织
├── 组织方式 1：按类型分（Flat）
│   ├── components/ 下全平铺
│   ├── 适合：小项目（< 10 个组件）
│   └── 缺点：组件多了找不到
├── 组织方式 2：按功能分（Feature-based）
│   ├── 每个功能模块一个文件夹

│   └── 优点：改一个功能只需进一个文件夹
├── 组织方式 3：按层级分（Atomic）
│   ├── components/base/、components/business/、views/
│   ├── 适合：有设计系统的大型项目
│   └── 优点：层级清晰，新人上手快
├── 文件命名约定
│   ├── PascalCase：UserCard.vue
│   ├── kebab-case：user-card.vue
│   └── 全项目保持一致即可
├── 组件内部结构顺序
│   ├── <script setup>（逻辑）
│   ├── <template>（模板）
│   └── <style scoped>（样式）
└── 核心原则
    ├── 一致性 > 完美
    ├── 可发现性（看名字知道在哪）
    └── 就近原则（相关文件放一起）
```

上一节你知道了组件是"积木"，也学会了写 `.vue` 文件。但新问题马上来了：项目里几十个组件到底放哪？全塞进 `components/` 平铺，还是按功能分子目录？组件里一个文件又该写多少东西？别小看这个问题——组织混乱的组件库，三个月后连作者自己都找不到"那个改订单状态的组件在哪"。

## 🤔 一、为什么文件组织很重要？

刚学 Vue 时，你可能把所有组件都扔到 `src/components/` 下：

```text
src/components/
├── Header.vue
├── Footer.vue
├── Sidebar.vue
├── UserCard.vue
├── ProductCard.vue
├── OrderTable.vue
├── LoginForm.vue
├── RegisterForm.vue
├── SearchBar.vue
├── Modal.vue
├── Button.vue
├── Input.vue
├── Chart.vue
├── ...（30 个文件平铺）
```

**3 个月后**：你打开这个文件夹——30 个 `.vue` 文件，想找一个"注册表单"？滚半天。

**这就是文件组织的意义**：**让任何人都能"一眼看懂"这个项目的组件在哪、怎么分类**。

> 💬 **老师备注**：Vue 官方没有强制规定目录结构，但社区有三种主流模式。**选哪一种不重要，重要的是"你团队的人都能看懂，且保持一致"**。

---

## 💡 二、三种主流组织方式

### 方式 1：按类型分（Flat 扁平）

```text
src/
├── components/
│   ├── Header.vue
│   ├── Footer.vue
│   ├── UserCard.vue
│   └── ...
└── views/
    ├── HomePage.vue
    ├── AboutPage.vue
    └── ...
```

**特点**：所有组件平铺在 `components/` 下，页面在 `views/` 下。

**优点**：简单，不需要纠结"放哪"。
**缺点**：超过 15 个组件就开始乱了。

**适合**：个人项目、演示项目、组件总数 < 15。

---

### 方式 2：按功能分（Feature-based）

```text
src/
├── modules/
│   ├── user/                       ← 用户模块
│   │   ├── components/
│   │   │   ├── UserCard.vue
│   │   │   ├── UserForm.vue
│   │   │   └── UserAvatar.vue
│   │   ├── composables/
│   │   │   └── useUser.js
│   │   └── UserPage.vue
│   │
│   ├── product/                    ← 商品模块
│   │   ├── components/
│   │   │   ├── ProductCard.vue
│   │   │   ├── ProductList.vue
│   │   │   └── ProductFilter.vue
│   │   ├── composables/
│   │   │   └── useProduct.js
│   │   └── ProductPage.vue
│   │
│   └── order/                      ← 订单模块
│       ├── components/
│       ├── composables/
│       └── OrderPage.vue
│
├── shared/                         ← 跨模块共享
│   └── components/
│       ├── BaseButton.vue
│       ├── BaseModal.vue
│       └── BaseInput.vue
│
└── App.vue
```

**特点**：每个业务模块自成一个独立文件夹，模块内部放自己的组件、逻辑、页面。

**优点**：
- **高内聚**：改"用户模块"只需要进 `modules/user/`
- **易删除**：删除"用户模块" = 删除整个文件夹
- **多人协作友好**：不同人改不同模块，互不干扰

**缺点**：项目初期结构看起来有点"重"。

**适合**：中大型项目、多人协作、组件 > 30。

> 💬 **老师备注**：这是 Vue 3 官方文档推荐的项目结构模式，也是目前 Vue 社区的主流选择。**如果你不确定选哪个，就选这个**。

---

### 方式 3：按层级分（Atomic 原子化）

```text
src/
├── components/
│   ├── base/              ← 原子级（全项目复用）
│   │   ├── BaseButton.vue
│   │   ├── BaseInput.vue
│   │   ├── BaseIcon.vue
│   │   └── BaseTag.vue
│   │
│   └── business/          ← 组合级（业务相关）
│       ├── UserCard.vue
│       ├── ProductCard.vue
│       ├── OrderTable.vue
│       └── CommentItem.vue
│
└── views/                 ← 页面级
    ├── HomePage.vue
    ├── ProductDetailPage.vue
    └── UserCenterPage.vue
```

**特点**：按组件的"抽象层级"分类，不按业务分类。

**优点**：层级清晰，新人知道"找基础组件去 base/，找业务组件去 business/"。
**缺点**：改一个功能可能要跨三个文件夹（base/、business/、views/）。

**适合**：有完善设计系统的大型项目、组件需要跨业务大量复用。

## 💡 三、混合模式（推荐）

实际项目中，最实用的是**混合模式**——结合"按功能"和"按层级"：

```text
src/
├── components/                     ← 全局共享组件（按层级）
│   ├── base/                       ← 基础组件
│   │   ├── BaseButton.vue
│   │   ├── BaseInput.vue
│   │   ├── BaseModal.vue
│   │   └── BaseTable.vue
│   └── business/                   ← 通用业务组件
│       ├── AppHeader.vue
│       ├── AppSidebar.vue
│       └── EmptyState.vue
│
├── views/                          ← 页面（按功能组织）
│   ├── student/                    ← 学生管理
│   │   ├── components/             ← 仅此页面用的组件
│   │   │   ├── StudentCard.vue
│   │   │   └── ScoreChart.vue
│   │   ├── StudentListPage.vue
│   │   └── StudentDetailPage.vue
│   │
│   ├── course/                     ← 课程管理
│   │   ├── components/
│   │   │   └── CourseSchedule.vue
│   │   └── CoursePage.vue
│   │
│   └── dashboard/                  ← 仪表盘
│       ├── components/
│       └── DashboardPage.vue
│
├── composables/                    ← 全局可复用的组合式函数
│   ├── useAuth.js
│   └── useRequest.js
│
├── stores/                         ← Pinia 状态管理
├── router/                         ← Vue Router 路由
└── App.vue
```

**分层逻辑**：
- `components/base/`——**全项目复用**，无业务逻辑
- `components/business/`——**跨页面复用**，有业务含义
- `views/xxx/components/`——**仅当前页面使用**，就近放置

> 💬 **老师备注**：注意 `views/student/components/` 这个设计——把"只在学生管理模块里用的组件"放在模块内部，而不是扔到全局 components/ 里。这叫**就近原则**：**相关文件放一起，改一个功能不用横跨整个项目**。

## 💡 四、文件命名约定

| 约定 | 例子 | 使用场景 |
|---|---|---|
| **PascalCase**（大驼峰） | `UserCard.vue` | 绝大多数 Vue 组件的标准命名 |
| **kebab-case**（短横线） | `user-card.vue` | 某些团队偏好，作为文件名也完全 OK |
| **Base 前缀** | `BaseButton.vue` | 标记"基础/原子组件" |
| **App 前缀** | `AppHeader.vue` | 标记"应用级组件"（如头部、侧栏、底部） |
| **The 前缀** | `TheHeader.vue` | 标记"全局唯一组件"（如全局 Loading） |

**核心原则**：**全项目统一就行，不用纠结用哪种**。

## 💡 五、单文件组件（.vue）内部结构顺序

Vue 官方推荐的三段式顺序：

```vue
<!-- 1. 逻辑（脑子） -->
<script setup>
// imports
// props / emits
// composables
// 响应式数据
// 计算属性
// 方法
</script>

<!-- 2. 模板（长相） -->
<template>
  <!-- HTML + Vue 指令 -->
</template>

<!-- 3. 样式（化妆） -->
<style scoped>
/* CSS */
</style>
```

> 💬 **老师备注**：Vue 官方推荐 `<script setup>` 放最前面——因为**逻辑是组件的核心**，放第一眼有助于快速理解。不过也有团队习惯 `<template>` 放前面，都行，统一即可。

> 💬 **进阶技巧**：`<script setup>` 默认没有组件名（文件名就是组件名），但在 Vue DevTools 中调试时，有时文件名不够直观。Vue 3.3+ 提供了 `defineOptions` 宏来手动设置组件名，在 `<script setup>` 中直接写：
> ```vue
> <script setup>
> defineOptions({ name: 'StudentScoreChart' })
> // 现在 DevTools 里看到的就是这个名字，方便定位
> </script>
> ```

<img src="../00-公共资源/图/03-组件化思想/图3-12.svg" alt="三种组件目录组织方式对比">

> `defineOptions` 不需要 import，编译器全局可用。它还可以设 `inheritAttrs: false` 等选项，遇到需要"在 setup 中配置组件选项"的场景时用它。

## ⚠️ 六、常见陷阱

### 陷阱 1：把一个"只在一个页面用"的组件扔到全局 components/

```text
src/components/StudentScoreChart.vue   ← 只在学生页面用，为什么要全局？

应该放：src/views/student/components/StudentScoreChart.vue
```

**原则**：**就近放置**——只在 A 页面用，就放在 A 页面的目录下。

### 陷阱 2：components/ 下出现 3 层以上的嵌套

```text
components/base/form/input/text/BaseTextInput.vue   ← 找这个文件花了 10 秒
```

组件目录最多 2 层嵌套（如 `base/` 下面直接放文件），超过说明你在"为了分层而分层"。

### 陷阱 3：混乱的命名风格

```text
components/
├── user-card.vue       ← kebab-case
├── ProductList.vue     ← PascalCase
├── base_button.vue     ← snake_case 🐍？
└── The-Header.vue      ← 混合？
```

**统一！统一！统一！** 选一种，全项目一致。

## 🧠 本节小结

- **为什么重要**：文件组织决定"三个月后还能不能找到代码"，比一时的写法更影响长期维护
- **三种主流方式**：按类型 Flat（简单）、按功能 Feature（业务清晰）、按层级 Atomic（组件库友好）
- **推荐混合模式**：页面组件就近放 + 通用组件进 `components/` + 按功能模块分区
- **命名约定**：多单词、PascalCase；文件与组件名一致，一眼知道"这是什么、属于哪"
- **内部结构顺序**：`<template>` → `<script setup>` → `<style scoped>`，自上而下读
- **两条红线**：只在一个页面用的组件别扔全局 `components/`；`components/` 嵌套别超过 3 层
