## 🤔 一、先讲个故事：不改的代码

张三写了一个电商项目的购物车功能，手动点了点，没问题，上线了。

三个月后，老板说："购物车要加一个优惠券功能。"张三改了几行代码，又手动点了点购物车，没问题，上线了。

结果第二天客服电话被打爆——用户说："加优惠券之后，删除商品按钮坏了！"

张三懵了：我就改了个优惠券，跟删除按钮有啥关系？

这就是**没有测试的后果**：你改 A 功能，B 功能悄悄坏了，你根本不知道。因为你不可能每次改完都手动把所有功能全点一遍。

### 测试解决的核心问题

**回归保护**：写一次测试，之后每次改代码，跑一遍测试，如果某个老功能坏了，测试立刻告诉你。

这就像你装了烟雾报警器：平时不管它，一旦着火（出 bug），它马上响。

## 💡 二、测试金字塔

前端测试有个经典模型叫"测试金字塔"——越往上越少、越慢、越贵，越往下越多、越快、越便宜。

```text
         /\        ← E2E（端到端测试）：几十个
        /  \          模拟用户操作整个系统
       /    \         "用户登录 → 加购物车 → 下单"
      /------\
     / 集成测试 \   ← 集成测试：上百个
    /            \    多个模块组合是否正常协作
   /--------------\
  /    单元测试      \ ← 单元测试：几百上千个
 /____________________\  单个函数/组件：输入 → 输出
```

### 2.1 单元测试（Unit Test）—— 金字塔的基石

**测什么**：一个函数、一个组件、一个工具方法的输入输出。

**特点**：
- 跑得极快（毫秒级），几百个测试几秒跑完
- 不依赖浏览器、网络、数据库
- 写完马上跑，开发时频繁跑

**Vue 中的典型单元测试**：

```js
// 测一个工具函数
import { formatPrice } from '@/utils/format'

test('formatPrice 格式化价格', () => {
  expect(formatPrice(99)).toBe('¥99.00')
  expect(formatPrice(0)).toBe('¥0.00')
})
```

```js
// 测一个组件
import { mount } from '@vue/test-utils'
import Counter from '@/components/Counter.vue'

test('点击按钮 count 应该 +1', async () => {
  const wrapper = mount(Counter)
  await wrapper.find('button').trigger('click')
  expect(wrapper.text()).toContain('1')
})
```

### 2.2 集成测试（Integration Test）—— 测协作

**测什么**：多个模块组合在一起是否正常配合。

比如：用户表单组件 + Pinia store + API 请求模块，三者协作能不能完成"提交注册"流程。

```js
test('提交注册表单 → store 更新 → API 调用', async () => {
  const wrapper = mount(RegisterForm, {
    global: { plugins: [createPinia()] }
  })
  await wrapper.find('input[name="email"]').setValue('test@qq.com')
  await wrapper.find('form').trigger('submit')
  // 验证 store 中数据正确
  const store = useUserStore()
  expect(store.email).toBe('test@qq.com')
})
```

### 2.3 E2E 测试（End-to-End）—— 测完整流程

**测什么**：模拟真实用户在浏览器里操作，从打开页面到完成一个业务流程。

**特点**：
- 启动真实浏览器，慢（秒级）
- 依赖后端服务、数据库
- 数量少但覆盖核心流程

**典型 E2E 测试**：

```js
// 用 Playwright 写的 E2E 测试
test('用户登录 → 浏览商品 → 加入购物车 → 下单', async ({ page }) => {
  await page.goto('http://localhost:5173')
  await page.click('text=登录')
  await page.fill('#email', 'test@qq.com')
  await page.fill('#password', '123456')
  await page.click('button:has-text("登录")')
  await expect(page).toHaveURL('/home')
})
```

### 2.4 一句话区分

| 测试类型 | 一句话 | 数量 | 速度 |
|----------|--------|------|------|
| 单元测试 | "这个函数算对了没？" | 几百上千 | 毫秒 |
| 集成测试 | "这几个组件合作正常吗？" | 上百 | 中等 |
| E2E 测试 | "用户能走完整个流程吗？" | 几十 | 秒 |

> 💬 **老师备注**：实际项目中，单元测试占 60%~70%，集成测试占 20%~30%，E2E 占 5%~10%。注意这个比例——不要一上来就写 E2E，先把单元测试写好。

## 🔑 三、Vue 项目的测试工具链

在 Vue 3 生态里，推荐的测试方案是 **Vitest + Vue Test Utils**。

| 工具 | 作用 | 类比 |
|------|------|------|
| **Vitest** | 测试框架：跑测试、断言、覆盖率 | 相当于 Jest，但更快，原生支持 ESM |
| **Vue Test Utils** | Vue 组件测试工具：挂载组件、查找元素、触发事件 | 专门为 Vue 设计的辅助库 |
| **happy-dom / jsdom** | 在 Node.js 中模拟浏览器 DOM | 让你在没有浏览器的情况下"渲染"组件 |
| **Playwright / Cypress** | E2E 测试框架 | 启动真实浏览器模拟用户操作 |

**它们的关系**：

```text
Vitest（测试框架，负责"跑"测试）
  ├── Vue Test Utils（负责"操作"Vue 组件）
  ├── happy-dom（负责"模拟"浏览器环境）
  └── @vitest/coverage-v8（负责"统计"代码覆盖率）
```

> 💬 **老师备注**：以前大家用 Jest，但 Jest 对 ESM 支持不好，配置麻烦。Vitest 是 Vue 团队核心成员打造的，跟 Vite 共用配置，开箱即用，已经是 Vue 3 项目的首选。

## 🛠 四、什么时候写测试？

很多同学问："开发都来不及，哪有时间写测试？"

其实不是"没时间写"，而是"还没被 bug 折磨够"。一个实用原则：

### 优先级排序

| 优先级 | 什么代码 | 原因 |
|--------|----------|------|
| 🔴 最高 | 工具函数、数据格式化、业务计算 | 纯逻辑，容易测，Bug 影响大 |
| 🟡 中等 | 核心组件（表单、列表、购物车） | 用户直接交互的部分 |
| 🟢 较低 | 纯展示组件、动画效果 | 测的价值不大 |

### TDD vs 后补测试

- **TDD（测试驱动开发）**：先写测试，再写代码。适合逻辑明确的功能。
- **后补测试**：先写功能，再补测试。适合大多数实际开发场景。

对于初学阶段，**建议先从后补测试开始**：功能写完了，跑一跑没问题，顺手把关键逻辑的测试写上。

## ⚠️ 五、常见误区

### 误区 1：「测试覆盖率 100% 才是好项目」

追求 100% 覆盖率通常会让你写大量无意义的测试（比如测一个 `return props.title` 的组件）。**80% 左右的覆盖率 + 覆盖核心逻辑，远好过 100% 的虚假安全感。**

### 误区 2：「手动点一点就够了，不用写测试」

手动测试只覆盖你"这次想到"的路径。测试代码覆盖的是"所有你写下来的"路径——而且每次改代码都能自动跑。

### 误区 3：「E2E 测试最接近用户，所以应该多写」

E2E 测试最"真实"但也最慢、最脆弱（网络抖一下就挂）。金字塔底部的单元测试才是性价比最高的。

---

## 🧠 本节小结

- **不写测试的风险**：改 A 功能 B 悄悄坏，手动回归成本高；测试 = 烟雾报警器，提供回归保护
- **测试金字塔**：单元测试（多、毫秒级、测函数/组件）→ 集成测试（适量、测模块协作）→ E2E（少、秒级、真实浏览器跑完整流程）
- **数量配比参考**：单元约 60%~70%、集成约 20%~30%、E2E 约 5%~10%
- **Vue 工具链**：Vitest（跑测试）+ Vue Test Utils（操作组件）+ happy-dom（模拟 DOM）+ Playwright / Cypress（E2E）；Vitest 与 Vite 同源、原生支持 ESM，已是 Vue 3 首选
- **优先级**：工具函数 / 数据格式化 / 业务计算 > 核心组件 > 纯展示组件；初学阶段建议后补测试，不必强上 TDD
- **三大误区**：100% 覆盖率 ≠ 好项目（80% + 核心逻辑更实在）；手动点一点覆盖不全；E2E 最真实也最慢最脆，别贪多
