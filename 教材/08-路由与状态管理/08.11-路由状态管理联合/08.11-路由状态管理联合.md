到这儿，路由的跳转、守卫和 Pinia 的状态仓库你都分别会用了。但真实系统里它们常常要打配合：用户刷新后台页面时，怎么知道该不该放行？登录状态放在 Pinia，可刷新一下就没了，守卫凭什么判断？这节把路由和状态管理串起来，解决「刷新丢登录」这类联合问题。

> 🎯 **类比一下：路由 × Store ≈ 前台接待 × 会员档案库**
> 路由像"前台接待"：决定你（导航）去哪个房间；Store 像"会员档案库"：记录你是谁、买了什么。接待员查档案库才能放行（守卫读 store 判断权限），档案库也要看接待员带谁来（路由参数更新 store）。两者各司其职又必须联动，缺一个系统就卡壳。

> 🧑 **小白**：刷新就丢登录，为什么不用 localStorage 直接存 token 就完事？
> 🤖 **Vue 君**：token 可以存 localStorage，但"用户身份详情"要放 store——刷新后拿 token 重新请求一次，再写回 store。
> 👨🏫 **老湿**：**一个口诀：能放进 URL 的（搜索词/页码）放 URL，全局共享的（用户/购物车）放 store，只在本组件的放本地**。

## 🤔 一、路由和 Store 为什么要联合？

路由负责"你在哪个页面"，Store 负责"页面里有什么数据"。很多场景下它们天然交织：

- 从 `/search?q=vue&page=2` 进入搜索页 → 路由提取 `q` 和 `page` → Store 发起搜索请求 → 展示结果
- 用户切换分页 → Store 更新 `page` → URL 同步为 `?page=3` → 用户可以复制链接分享

这节的目标是让你掌握这种"路由 ↔ Store"的双向联动模式。

## 💡 二、守卫 + Store：权限控制

```js
// stores/auth.js
import { ref, computed } from 'vue'      // ⚠️ computed 必须一起导入
import { defineStore } from 'pinia'

export const useAuthStore = defineStore('auth', () => {
  const user = ref(null)  // null = 未登录

  const isLoggedIn = computed(() => !!user.value)
  const isAdmin = computed(() => user.value?.role === 'admin')

  async function login(credentials) { /* ... */ }
  function logout() { user.value = null }

  return { user, isLoggedIn, isAdmin, login, logout }
})
```

```js
// router/index.js
import { createRouter, createWebHistory } from 'vue-router'
import { useAuthStore } from '../stores/auth'

const router = createRouter({
  history: createWebHistory(),
  routes: [
    {
      path: '/dashboard',
      component: () => import('../views/Dashboard.vue'),
      meta: { requiresAuth: true }
    },
    {
      path: '/admin',
      component: () => import('../views/Admin.vue'),
      meta: { requiresAuth: true, role: 'admin' }
    },
    {
      path: '/login',
      component: () => import('../views/Login.vue'),
      meta: { guest: true }
    },
  ]
})

// 全局守卫：Pinia store 必须在 router 安装之后才能用
router.beforeEach((to, from) => {
  // ⚠️ 注意：这里 useAuthStore() 必须在 app.use(pinia) 之后调用
  // 因此 beforeEach 中的 Pinia 调用是安全的
  const auth = useAuthStore()

  // 需要登录但未登录 → 踢到登录页
  if (to.meta.requiresAuth && !auth.isLoggedIn) {
    return { path: '/login', query: { redirect: to.fullPath } }
  }

  // 已登录但角色不符
  if (to.meta.role && auth.user?.role !== to.meta.role) {
    return '/403'
  }

  // 已登录用户访问登录页 → 重定向
  if (to.meta.guest && auth.isLoggedIn) {
    return '/'
  }

  return true
})

export default router
```

> 💬 **老师备注**：`main.js` 里 `app.use(pinia)` 必须在 `app.use(router)` 之前，否则守卫里 `useAuthStore()` 会报错。顺序很重要：`createApp → createPinia → app.use(pinia) → app.use(router) → mount`。

## 🔑 三、路由参数驱动 Store

搜索页是最典型的场景：URL 里的 `?q=vue&page=2` 是"真相来源"（source of truth），Store 根据它来加载数据。

```vue
<!-- src/views/SearchPage.vue -->
<script setup>
import { watch } from 'vue'
import { useRoute } from 'vue-router'
import { useSearchStore } from '../stores/search'

const route = useRoute()
const searchStore = useSearchStore()

// 路由参数变化 → 更新 store → 发请求
watch(
  () => [route.query.q, route.query.page],
  ([q, page]) => {
    searchStore.search(q || '', Number(page || 1))
  },
  { immediate: true }  // 首次进入也触发
)
</script>

<template>
  <div>
    <p>搜索词：{{ route.query.q }}</p>
    <p>当前页：{{ route.query.page }}</p>
    <div v-if="searchStore.loading">加载中...</div>
    <div v-for="item in searchStore.results" :key="item.id">
      {{ item.title }}
    </div>
  </div>
</template>
```

## 🛠 四、Store 同步回 URL

反过来，用户在页面内切换分页，URL 也要跟着变，这样用户才能复制链接分享：

```js
// stores/search.js
import { ref } from 'vue'
import { defineStore } from 'pinia'
// 注意：这里没有 import useRouter —— store 里不该感知路由

export const useSearchStore = defineStore('search', () => {
  const keyword = ref('')
  const page = ref(1)
  const results = ref([])
  const loading = ref(false)

  async function search(q, p) {
    keyword.value = q
    page.value = p
    loading.value = true
    // 模拟请求
    await new Promise(r => setTimeout(r, 300))
    results.value = [{ id: 1, title: `搜索结果: ${q} - 第${p}页` }]
    loading.value = false
  }

  return { keyword, page, results, loading, search }
})
```

**路由跳转放到组件层**：

```vue
<script setup>
import { useRouter } from 'vue-router'
import { useSearchStore } from '../stores/search'

const router = useRouter()
const searchStore = useSearchStore()

function goToPage(newPage) {
  // 组件负责「跳到哪去」，store 只负责「数据变成什么样」
  searchStore.search(searchStore.keyword, newPage)
  router.push({
    query: { q: searchStore.keyword, page: newPage }
  })
}
</script>
```

> 💬 **老师备注：为什么 store 里不能调 `useRouter()`？**
> `useRouter()` 内部是 `inject()`。而 setup store 的函数体是在**store 实例化时**执行的，那时**没有活动的组件实例**，会抛出警告 `inject() can only be used inside setup()`，拿到的 `router` 是 `undefined`，后面 `router.push()` 直接 TypeError。
>
> 记住这条分工：**store 管"数据变成什么样"，组件和路由管"跳到哪去"。** 状态管理和视图导航是两条线，不要交叉——这也是本节标题"路由 + 状态管理联合"里"联合"的真正含义：**在组件里联合，不是在 store 里联合。**

## 🛠 五、什么放 URL，什么放 Store？

| 放哪里 | 适用场景 | 例子 |
|---|---|---|
| **URL** | 需要分享 / 书签 / 前进后退的状态 | 搜索词、分页页码、Tab、筛选条件 |
| **Store** | 跨页面共享、不需要持久到 URL | 用户信息、购物车、通知 |
| **组件局部** | 只在当前组件/页面使用的状态 | 模态框开关、表单输入 |

一个简单判断：**如果用户刷新页面后这个状态丢了会不会困惑？** 如果会 → 放 URL。如果不会（比如购物车在 checkout 过程中刷新）→ 可以考虑本地存储。

## ⚠️ 六、常见陷阱

### 陷阱 1：守卫里 `useStore()` 的时机

```js
// ❌ main.js 中 app.use(router) 在 app.use(pinia) 之前
const app = createApp(App)
app.use(router)      // ← 先装路由
app.use(pinia)       // ← 后装 Pinia
// → 守卫里 useStore() 报错

// ✅
app.use(pinia)       // ← 先装 Pinia
app.use(router)      // ← 后装路由
```

### 陷阱 2：URL ← Store 的死循环

```js
// ❌ watch store.page → router.push（改 URL）→ watch route.query → 改 store.page → ...
// 这会造成死循环
```

解法：在 `watch` 里加防抖，或者在 store 里加标志位跳过不必要的更新。

### 陷阱 3：所有状态都放 Store

Store 是全局的，组件卸载后状态还在。很多只在当前页面用的状态（比如一个表单的输入值），放 Store 反而增加心智负担，放组件内部就好。

## 🧠 本节小结

- **为什么联合**：路由守卫要判权限，权限数据放 store；URL 又常是页面状态的"唯一事实来源"
- **守卫里用 store**：直接 `useAuthStore()` 读取登录态即可，注意 pinia 实例要先于守卫执行初始化（`app.use(pinia)`）
- **刷新丢状态**：store 在内存、刷新即失；配合持久化（localStorage 等）在启动时恢复登录态
- **URL ↔ store 双向同步**：如搜索词既放 URL query 又放 store，需约定谁是主，避免死循环
- **职责边界**：URL 管"在哪一页"，store 管"页面需要什么数据"，别把大对象塞进 query

> 🧊 **冷知识**："搜索词该放 URL 还是 store"有个很实用的判断标准：**用户会不会复制这条链接发给别人？** 会 → 放 URL（分享后对方打开能还原同样页面）；不会 → 放 store。这也是"URL 是页面状态的唯一事实来源（Source of Truth）"这句工程格言在日常最朴素的应用——可分享、可书签、可刷新恢复。

<details><summary>🔍 想深究再看：URL ↔ store 双向同步怎么避免"死循环"？</summary>

经典反模式：`watch(store.page)` → `router.push('?page=3')` → `watch(route.query)` → 又写回 `store.page` → 又触发第一个 watch……循环往复。三种常规解法：①**约定单向主从**——URL 是主、store 是从（只在路由变化时写 store，不反向推 URL）；②watch 里加**防抖/去重标志位**，相同值直接跳过；③用 `router.replace` 且**不监听自己刚写入的值**。工程上最推荐 ①：谁有"刷新后还能还原"的使命，谁就当主。

</details>
