## 🤔 一、先问：为什么状态管理会诞生？

第 3 章讲过：组件多了之后，同一份数据要在多个组件间同步，会变成灾难。常见的三种土办法：

| 做法 | 问题 |
|---|---|
| 一层层 props 传 | 中间层被迫当"二传手"，改个字段名要动整条链 |
| 一层层 emit 往上抛 | 同上，而且组件被迫耦合业务 |
| 挂到 `window` / 全局变量 | 能用，但**不响应式**——数据变了界面不更新 |

所以需要一种"**共享 + 响应式**"的方案。这就是状态管理库的诞生原因。而 Vuex 是 Vue 2 时代的答案，**Pinia 是 Vue 3 时代的答案**。

## 💡 二、Vuex → Pinia 概念对照（⭐ 本节最有价值的部分）

读懂这张表，你就能看懂任何 Vuex 老代码：

| Vuex | Pinia | 说明 |
|---|---|---|
| `state` | `state`（或直接用 `ref`） | 存放原始数据 |
| `getters` | `getters`（或直接用 `computed`） | 派生/计算数据 |
| `mutations` | **没有对应物** | Pinia 里**直接改 state**（在 store 内部），不需要 mutations |
| `actions` | **没有对应物** | Pinia 里同步异步都是 action，但不用"action 才能异步"的约定 |
| `module` / `namespaced` | **每个 store 文件就是一个模块** | 天然隔离，不需要 namespace 概念 |
| `createStore()` | `createPinia()` + `defineStore()` | 初始化方式 |
| `mapState` / `mapGetters` | `storeToRefs()` | 组件里取值的方式 |

### 看到老代码时怎么读

```js
// ── Vuex 老代码 ──
export default new Vuex.Store({
  state: { count: 0 },
  mutations: {
    increment(state) { state.count++ }        // ← 同步改 state
  },
  actions: {
    async fetchData({ commit }) {             // ← 异步，然后 commit
      const res = await api.get()
      commit('setData', res)
    }
  }
})
// 组件里：
this.$store.state.count             // 读 state
this.$store.dispatch('fetchData')  // 调 action
this.$store.commit('increment')    // 调 mutation
```

```js
// ── Pinia 新写法（同样的功能）──
export const useCounterStore = defineStore('counter', () => {
  const count = ref(0)
  async function fetchData() {                 // 异步：直接写函数，没有 action/mutation 之分
    const res = await api.get()
    data.value = res
  }
  return { count, data, fetchData }
})
// 组件里：
const counter = useCounterStore()
const { count } = storeToRefs(counter)   // 解构保持响应式
counter.fetchData()                      // 直接调，不用 dispatch
```

> 💬 **老师备注：读 Vuex 老代码的三条线索**
> 1. 看到 `commit(...)` → 在调 mutation（同步改 state）
> 2. 看到 `dispatch(...)` → 在调 action（可能异步）
> 3. 看到 `mapState` / `namespaced: true` → 这是 Vuex 特有的模块化语法
>
> 有了这张表，你不需要会写 Vuex，只需要**读得懂**。

## 🔑 三、那为什么 Pinia 取代了 Vuex？

官方在 Vuex 4 之后明确标注：**Vuex 仍会维护，但不会再新增功能**。Pinia 全面胜出的原因有四个：

| 维度 | Vuex | Pinia |
|---|---|---|
| **概念数量** | state/getters/mutations/actions/module 五套 | 基本只有 state + actions，**认知负担小一半** |
| **TypeScript** | 需要复杂的类型体操 | 类型推导天然，开箱即用 |
| **体积** | 较大 | 约 1KB，**tree-shaking 友好**（只用到哪个 store 就打包哪个） |
| **写法** | 必须 `mutations` 里改 | store 内**直接改** state |

**还有一个最实在的理由**：Pinia 的 setup store 里，你可以像写普通组件一样用 `ref` / `computed` / 函数——**迁移成本极低**。

## ⚠️ 四、那 Vuex 还需要学吗？

**需要"认识"，不需要"学会"。**

判断标准很简单：

| 场景 | 该怎么办 |
|---|---|
| **新项目** | 直接用 Pinia，**不要碰 Vuex** |
| **接手 / 维护老项目** | 认得上五大概念就够，能读能改就行 |
| **面试** | 能说清 Pinia 相比 Vuex 解决了什么问题，是加分项 |
| **第 12 章综合项目** | **完全不用 Vuex**——后续所有实战（08.9~08.13）以及第 12 章都只用 Pinia |

> 💬 **老师备注**：如果时间紧，**这一节可以只读上面的"概念对照表"**，其余跳过。真正要学 Pinia，直接进 8.8。
>
> 但如果你是那种"看到新东西就想搞懂"的学习者——那至少要知道 Vuex 五个概念是什么，因为**十年前的中文技术文章里九成讲的是 Vuex**，网上搜到的东西会反复提到它。
