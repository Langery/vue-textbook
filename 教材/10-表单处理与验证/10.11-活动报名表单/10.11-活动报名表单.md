## 🎯 项目需求（一句话）

做一个"跳蚤市集活动报名"表单：姓名、手机号、想报名的场次（下拉）、是否带闲置物品（勾选）、备注（可选）；带必填与手机号格式校验，提交时 loading + 防重复，成功后清空表单并展示"报名成功"卡片——全程只用第 10 章已学的 VeeValidate 能力（或课堂 10.3 的手写验证框架，二选一），并仿照 10.9 把逻辑抽成 composable。

### ✅ 验收标准（能跑、能展示）

- [ ] 项目能 `npm run dev` 启动，页面是一张完整的"活动报名"表单
- [ ] 姓名为空失焦时报"必填"；手机号格式不对时报错；场次未选时报"请选择场次"
- [ ] 提交按钮点击后进入 loading（文案变"提交中…"）并禁止重复点击
- [ ] 模拟提交成功（0.8 秒）后：按钮恢复、表单清空、页面显示"报名成功，活动前一天短信提醒"

- [ ] 能向同学讲清：`handleSubmit` 返回的函数为什么能安全地做 loading / 防重复？`resetForm` 之后校验状态为什么也要一起清掉？

## 🛠 分步提示（3~5 步，含关键代码锚点）

> 以下只给路线和关键锚点，**不贴全量答案**。卡住时回头翻 10.4 / 10.5 / 10.6 / 10.7 / 10.9 对应小节。

### Step 1：注册全局规则（回顾 10.5 / 10.7）

在 `main.js`（或独立 `rules.js`）里用 `defineRule` 注册两条规则：`required`（非空）与 `phone`（手机号格式，可参考 10.7 的课堂实现），再用 10.5 的方式全局 `extend` 或按需注册。锚点检查：任意输入框给 `rules="required"` 后，清空失焦即报"必填"。

### Step 2：搭 `useForm` 骨架（回顾 10.4 / 10.6）

字段定为 `name`、`phone`、`session`（场次）、`bringItem`（是否带闲置，布尔）、`remark`（备注）。用 `useForm({ validationSchema: {...} })` 声明校验规则（schema 形式或每条规则字符串均可，按课堂习惯来），解出 `handleSubmit`、`errors`、`values`、`resetForm`。

### Step 3：写"报名"提交逻辑（回顾 10.6 的 loading 与防重复）

先做一个假提交函数 `submitSignup(payload)`：`new Promise` 延迟 800ms 后 resolve（模拟给后端），在 `handleSubmit` 的回调里 `await` 它：

```js
const { isSubmitting, handleSubmit, resetForm, ... } = useForm({ ... })

const onSubmit = handleSubmit(async (values) => {
  await submitSignup(values)          // 模拟接口，内部自己管理 loading
  success.value = true                // 显示"报名成功"卡片
  resetForm()                         // 成功后清空表单（回顾 11.6：校验状态一并清）
})
```

> 锚点检查：疯狂连点提交按钮，只发出一次"提交中"；成功后表单所有字段与错误提示都回到初始态。

### Step 4：模板绑定五种输入 + 错误展示（回顾 10.1 / 10.2 / 10.7）

用 `useField` 或 `useForm` 的 `defineField` 把 `name`（text）、`phone`（text + `inputmode="numeric"`）、`session`（select，含"9:00-11:00 场 / 14:00-16:00 场 / 19:00-21:00 场"）、`bringItem`（checkbox）、`remark`（textarea）绑进模板；每项下方用 `errors.xxx` 展示红字错误，提交失败可聚焦到第一个错误字段。样式做到"错误时输入框红边"，参考 10.7 的交互体验。

### Step 5：抽成 `useSignup` composable（回顾 10.9）

把 `useForm` 的配置、校验 schema、`onSubmit` 成功/失败处理全部搬进 `src/composables/useSignup.js`，返回 `errors / isSubmitting / handleSubmit / success` 等，组件里只留：

```js
const { errors, isSubmitting, handleSubmit, success } = useSignup()
```

并让"报名成功"卡片在 `success` 为真时显示，关闭按钮把它置回 `false`。

**`src/rules.js`** —— 规则库单独一个文件，是为了让"规则"能跨表单复用（回顾 10.5 的 `defineRule`）：

```js
import { defineRule } from 'vee-validate'

// ① 必填：空字符串 / 纯空格 / 未勾选的 false 都算「没填」
defineRule('required', (value) => {
  if (typeof value === 'string') {
    return value.trim() === '' ? '这一项必须填写' : true
  }
  if (typeof value === 'boolean') {
    return value ? true : '请勾选这一项'
  }
  return value === null || value === undefined || value === ''
    ? '这一项必须填写'
    : true
})

// ② 手机号：1 开头、第二位 3-9、共 11 位
defineRule('phone', (value) => {
  if (!value) return true   // 空值交给 required 去报，避免两条规则重复骂人
  return /^1[3-9]\d{9}$/.test(String(value).trim())
    ? true
    : '手机号格式不对（应为 1 开头的 11 位数字）'
})

// ③ 场次：下拉框必须真的选了一个值
//    ⚠️ 这里故意不用 required——业务上「必须从三场里挑一个」
//    需要一句专门的提示语，所以单开一条规则
defineRule('pickSession', (value) => (value ? true : '请选择一个场次'))

// ④ 备注：选填，但限长 50 字，超了给提示（顺带演示带参数的规则）
defineRule('maxRemark', (value, [limit]) => {
  if (!value) return true
  return String(value).length <= Number(limit)
    ? true
    : '备注最多 ' + limit + ' 字'
})
```

**`src/composables/useSignup.js`** —— 表单的全部逻辑（回顾 10.9 的抽离姿势）：

```js
import { ref } from 'vue'
import { useForm } from 'vee-validate'
import '../rules'   // 触发 defineRule 注册（回顾 10.5）

export const SESSIONS = [
  { value: 'am', label: '上午场 9:00 - 11:00（主会场）' },
  { value: 'pm', label: '下午场 14:00 - 16:00（图书馆前）' },
  { value: 'night', label: '夜场 19:00 - 21:00（操场夜市）' }
]

// 假接口：800ms 后 resolve，模拟把报名单发给后端（回顾 10.6）
function submitToServer(payload) {
  return new Promise((resolve) => {
    setTimeout(() => {
      resolve({ code: 0, ticket: 'MKT-' + Math.random().toString(36).slice(2, 8).toUpperCase() })
    }, 800)
  })
}

export function useSignup() {
  const {
    defineField,      // ⭐ useForm 4 里取字段值的唯一正解
    handleSubmit,
    errors,
    isSubmitting,    // 提交中：VeeValidate 自动维护（回顾 10.6）
    resetForm,
    values
  } = useForm({
    validationSchema: {
      name: 'required',
      phone: 'required|phone',
      // ⚠️ 这里只写 pickSession，不写 'required|pickSession'。
      // 规则链是「顺序短路」的：第一条不通过，后面的根本不跑。
      // 写成 required|pickSession 时，空值会先被 required 拦下，
      // pickSession 精心写的「请选择一个场次」永远轮不到出场。
      session: 'pickSession',
      remark: 'maxRemark:50'
      // bringItem 是选填的 checkbox，故意不给任何规则
    },
    initialValues: {
      name: '',
      phone: '',
      session: '',
      bringItem: false,
      remark: ''
    }
  })

  // ===== 字段：defineField 返回 [值, 属性]，值才能 v-model =====
  const [name, nameAttrs] = defineField('name')
  const [phone, phoneAttrs] = defineField('phone')
  const [session, sessionAttrs] = defineField('session')
  const [bringItem, bringItemAttrs] = defineField('bringItem')
  const [remark, remarkAttrs] = defineField('remark')

  const success = ref(false)
  const ticket = ref('')
  // ⚠️ 快照：成功卡片上要显示「谁报的名」，但 resetForm() 会把 name 清空。
  // 如果直接 :name="name" 绑活动字段，卡片会变成「，你已收到报名凭证」——
  // 提交那一刻的名字必须在这里另存一份。
  const signedName = ref('')

  // ⚠️ 防重复提交用的是「自建锁」，不是 isSubmitting。
  // 原因：VeeValidate 是「先置 isSubmitting = true，再调用你的回调」，
  // 所以回调第一行写 if (isSubmitting.value) return 会永远命中——
  // 表单看着一切正常，却一次都提交不出去（而且不报错，极难排查）。
  // 正确分工：isSubmitting 负责「禁用按钮」，自建锁负责「逻辑兜底」。
  let locked = false

  // ⭐ handleSubmit 立即执行并返回真正的提交函数——必须在 script 里接住，
  //   模板里只写 @submit="onSubmit"。直接在模板写 handleSubmit(cb) 会静默失效。
  const onSubmit = handleSubmit(async (formValues) => {
    if (locked) return
    locked = true

    try {
      const res = await submitToServer(formValues)
      ticket.value = res.ticket
      signedName.value = formValues.name
      success.value = true
      // 值 + 错误 + touched 一起归零，表单才真正回到「全新」状态
      resetForm()
    } finally {
      locked = false
    }
  })

  function closeSuccess() {
    success.value = false
  }

  return {
    sessions: SESSIONS,
    name, nameAttrs,
    phone, phoneAttrs,
    session, sessionAttrs,
    bringItem, bringItemAttrs,
    remark, remarkAttrs,
    errors,
    values,
    isSubmitting,
    onSubmit,
    success,
    ticket,
    signedName,
    closeSuccess
  }
}
```

|---|---|---|
| 直接写 `<input v-model="username">` 而**不**先 `defineField('username')` | 控制台报 `username is not defined`，输入框根本收不到字——**`useForm()` 不暴露字段值给 v-model** | 10.4 useField/defineField |
| 把 `@submit="onSubmit"` 改成 `@submit="handleSubmit(onSubmit)"` | 表单彻底点不动、**且不报任何错**：那行代码在渲染时执行一次、产出一个没人调用的函数 | 10.4 handleSubmit 陷阱 |
| 把 schema 里 `session` 改成 `'required\|pickSession'` | 场次为空时提示变成干巴巴的「这一项必须填写」，而不是精心写的「请选择一个场次」——**规则链第一条不通过，后面根本不跑** | 10.4 规则链短路 |
| 手机号填 `1380013800`（10 位）和 `23800138000`（第二位非 3-9） | 两种都报同一条格式错误——正则 `/^1[3-9]\d{9}$/` 把长度和号段都管住了 | 10.5 自定义规则 |
| 备注填 60 个字 | 报「备注最多 50 字」——`maxRemark:50` 的 `50` 正是 `defineRule` 第二个参数解构出来的 `limit` | 10.5 带参数的规则 |

<details>
<summary>💬 老师备注：这个成品里有三处"故意的非标准写法"，都是真实项目会栽的跟头</summary>

**① 防重复提交用的是自建 `locked`，不是 `isSubmitting`。**
这一处最反直觉，也最容易把人卡住。10.6 教你写 `if (submitting.value) return` 做双保险——但那是因为 `submitting` 是**你自己声明的 ref**。一旦你改用 VeeValidate 白送的 `isSubmitting`，这行代码就会**永远命中**：

```
handleSubmit 内部顺序 → ① 置 isSubmitting = true → ② 调用你的回调
                                        ↑ 你的回调执行时它已经是 true 了
```

于是 `if (isSubmitting.value) return` 每次都直接 return，**表单看着一切正常（校验过了、按钮能点），却一次都提交不出去，而且控制台一声不吭**。这不是我推演的，是本实战的挂载测试真的跑出来的：断言"提交后按钮变『提交中…』"直接失败，加日志才看到回调里 `isSubmitting` 已经是 `true`。

正确分工是：**`isSubmitting` 负责 UI（`:disabled` + 文案切换），自建的 `locked` 负责逻辑（挡住并发的第二次调用）**。两者不是重复，是"给人看的"和"给机器看的"。

顺带说清 `handleSubmit` 自己其实已经拦了并发（内部有 `isPending` 判断），那为什么还要 `locked`？因为它是**实现细节**，不是文档承诺。将来你升级 VeeValidate、或者把 `@submit` 改成手动 `validate()` 再提交，这层保护就没了。**关键路径上的防线，不要依赖别人的内部实现。**

**② `session` 的 schema 只写 `pickSession`，不写 `'required|pickSession'`。**
规则链 `a|b|c` 是**顺序短路**的：第一条不通过，后面的压根不执行。`required` 对空值 `''` 判定为不通过，于是 `pickSession` 里那句精心写的「请选择一个场次」**永远轮不到出场**，用户看到的是干巴巴的「这一项必须填写」。

这带来一条通用规则：**当你为某个字段写了自定义规则、想输出专属提示语时，就不要在同一位置再挂 `required`**——把"空值判断"也收进你自己的规则里。要么像上面这样让自定义规则自己管空值，要么就用 `defineErrorMessage` 全局改 `required` 的文案，**别让两条规则抢同一个失败原因**。

对比一下 `phone` 字段为什么能写 `'required|phone'`？因为 `phone` 规则开头有一句 `if (!value) return true`——**空值主动放行，交给 `required` 去报**。两条规则职责不重叠，短路才安全。所以关键不是"能不能串"，而是"每条规则失败的原因会不会撞车"。

**③ 成功卡片上的姓名用 `signedName` 快照，不是直接绑 `name`。**
需求是"成功后清空表单**并**展示成功卡片"，这两个要求天然打架：`resetForm()` 把 `name` 清成 `''`，而卡片要显示"林小满，你已收到报名凭证"。如果图省事写 `:name="name"`，卡片会渲染成「**，**你已收到报名凭证」——一个句号孤零零杵在那儿。挂载测试里那条"卡片里显示了姓名"的断言就是这么失败的。

正解是**在 `resetForm()` 之前先把要留的信息另存一份**：

```js
signedName.value = formValues.name   // 快照
resetForm()                          // 再清空
```

顺序不能反。这条经验在真实项目里非常通用：任何"提交成功后清空表单 + 展示回执"的需求（注册成功页、下单成功页、报名凭证）都需要**先存后清**。同理，校验失败的场景要**先清后存**（保留用户数据）——10.6 说过"失败不清空，成功才清空"，这里补上"成功清空前记得留快照"就完整了。

**最后留个思考题**：`rules.js` 里 `required` 为什么要单独处理 `typeof value === 'boolean'` 这一支？提示：把本实战的 `bringItem` 从"选填 checkbox"改成"必勾选"，然后在 schema 里写 `bringItem: 'required'`，如果你没有那支会怎样？

## 🔮 它在最后的大项目里长成什么

这一节的"活动报名表单"，就是大项目 **Campus2Hand 校园二手集市**的**表单公共方案雏形**：发布闲置（标题/价格/成色/图片）、登录注册（账号密码 + 查重）、收货信息（姓名/手机/地址）——大项目里这三类表单的校验与提交，全都会复用本实战的配方：全局 `defineRule` 规则库 + `useForm` 封装 + 抽成 `useXxx` composable + 成功 `resetForm`。第 12 章写表单时，你会觉得每一步都是熟路。

> 🧊 **冷知识**：为什么"成功后 `resetForm()`"要连验证状态一起清？因为 VeeValidate 的 `resetForm` 默认会把 `errors`、`isValid`、`meta` 全部重置回初始态——如果你只清 `values` 不清 `errors`，用户填下一单时会看到上一单的红色错误"幽灵残留"。这也是"提交成功重置"的标准姿势：**值、错误、状态三件套一起归零**，表单才真正回到"全新"状态。

<details><summary>🔍 想深究再看：`handleSubmit` 为什么能"安全地做 loading / 防重复"？</summary>

`handleSubmit` 返回的包装函数在 VeeValidate 内部做了两件关键事：①**自动等待验证**——先全量校验，通过才调用你的回调；②**提供 `isSubmitting` 状态**——回调执行期间为 `true`（即使回调内部是 `async` 函数）。所以模板里 `:disabled="isSubmitting"` 就能在请求未返回时锁住按钮；再配合回调开头 `if (isSubmitting.value) return` 的双保险，连点、双击都只会触发一次提交。这就是"声明式 API 帮你管好状态机"的体现——手写版你得自己维护 `submitting` 布尔，VeeValidate 直接送给你。
