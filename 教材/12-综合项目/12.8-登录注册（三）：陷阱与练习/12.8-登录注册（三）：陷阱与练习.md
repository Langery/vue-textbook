## ⚠️ 一、常见陷阱

登录注册是整个项目的"门面"——登录都进不去，后面什么都白搭。这 4 个坑是初学者最容易踩的，每个都按「错误代码 → 正确代码 → 原因与排查要点」三件套讲清楚，看完就能照着改。

### 陷阱 1：Pinia 在 `main.js` 之前使用

```js
// ❌ 错误：在 createPinia() 之前调用 useUserStore()
import { useUserStore } from '@/stores/user'

const userStore = useUserStore()   // 报错！
const app = createApp(App)
app.use(createPinia())
```

```js
// ✅ 正确：先安装 Pinia，再使用 store
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'
import { useUserStore } from '@/stores/user'

const app = createApp(App)
app.use(createPinia())            // ① 先安装

// ② 之后才能在组件外使用 store
const userStore = useUserStore()
userStore.fetchSomething()
```

**原因**：`useUserStore()` 内部依赖"当前激活的 Pinia 实例"。在 `app.use(createPinia())` 之前，Pinia 还没被激活，调用就会抛错：`getActivePinia() was called but there was no active Pinia. Did you forget to install pinia?`。组件内部使用 store 一般不会踩这个坑（组件挂载必然在 app 创建之后），真正容易踩的是**路由守卫、工具函数、拦截器**这些"组件外"代码。

**排查要点**：
1. 看报错信息里有没有 `no active Pinia` —— 有就是没安装或安装顺序错了；
2. 检查 `useUserStore()` 是否写在 `app.use(createPinia())` 之前；
3. 检查是否在非组件环境（如 `router/index.js`、`api/index.js`）使用 store 且没有传入 pinia 实例；
4. 终极排查：全项目搜 `useUserStore(`，逐个确认都在 `main.js` 安装 Pinia 之后执行。

### 陷阱 2：localStorage 存对象不序列化

```js
// ❌ 错误：直接存对象 → localStorage 里变成 "[object Object]"
localStorage.setItem('userInfo', res.data.user)

// 读出来更惨："[object Object]" 拿不到任何字段
const user = localStorage.getItem('userInfo')
console.log(user.nickname)   // undefined
```

```js
// ✅ 正确：写入前 JSON.stringify，读取后 JSON.parse
localStorage.setItem('userInfo', JSON.stringify(res.data.user))

// 读取时注意兜底：没有数据时 getItem 返回 null，直接 JSON.parse(null) 会得到 null
// 但 JSON.parse(undefined) 会直接抛错，所以用 || 'null' 保证安全
const userInfo = JSON.parse(localStorage.getItem('userInfo') || 'null')
console.log(userInfo?.nickname)
```

**原因**：localStorage 只能存**字符串**。存对象时 JS 会自动调用 `toString()`，普通对象就变成了 `"[object Object]"`。存数组会变成 `"1,2,3"`，同样丢失结构。

**排查要点**：
1. 打开 DevTools → Application → Local Storage，看值是不是 `[object Object]` —— 是就说明没序列化；
2. 读取时 `JSON.parse` 抛 `Unexpected token` 报错，说明里面存的不是合法 JSON（可能存了两遍）；
3. 顺手提醒：**token 是字符串，不需要 JSON.stringify**，直接 `setItem('token', xxx)` 即可，别画蛇添足；
4. 改完记得清一下旧的脏数据（`localStorage.removeItem('userInfo')`），否则读出来还是坏的。

### 陷阱 3：路由守卫死循环

```js
// ❌ 错误：每次跳转 /login 又触发守卫，无限循环
router.beforeEach((to, from, next) => {
  if (!token) {
    next('/login')  // 又触发 beforeEach... 然后又 next('/login')... 浏览器卡死
  }
})
```

```js
// ✅ 正确：与 12.3 保持一致，用 meta.requiresAuth 判断（推荐）
// 这份路由表在 12.3 已经定稿：公开页 requiresAuth: false，需登录页 true
router.beforeEach((to) => {
  const userStore = useUserStore()

  // ① 已登录 → 放行
  if (userStore.token) return true

  // ② 未登录，但目标页本来就不需要登录（如 /home、/login）→ 放行
  if (to.meta.requiresAuth === false) return true

  // ③ 未登录且目标页需要登录 → 去登录页，带上来源地址
  return `/login?redirect=${encodeURIComponent(to.fullPath)}`
})
```

**原因**：往`/login` 跳转会**再次触发** `beforeEach`。用 `meta.requiresAuth` 判断时，`/login` 自己标了 `requiresAuth: false`，会走第② 步正常放行，**天然不会死循环**——不需要额外维护一份白名单数组。

**排查要点**：
1. **登录页自己的 `meta.requiresAuth` 必须是 `false`**。这是整套逻辑能跑通的前提。
2. 用 `=== false` 精确比较，而不是 `if (!to.meta.requiresAuth)`——后者会把"没写 meta 的路由"也判成需要登录，将来新增页面忘了标就会莫名被拦。
3. 已登录分支漏掉 `return` → 登录了还被拦，多半是 `if (userStore.token)` 后面没写 `return true`。
4. 浏览器卡死先别慌，关掉标签页，然后对着守卫代码逐条过一遍分支——死循环只有一个成因：**每次都往同一个受保护页面跳**。

> 💬 **老师备注：为什么不推荐"白名单数组"那种写法？**
> 它当然也能跑，但有个隐性成本：**白名单和路由表是两套数据**。以后新增一个公开页面（比如活动页 `/promotion`），你要记得改两个地方——加路由 + 加白名单。**漏一个，那个页面就登不上也逛不了。**
> 而 `meta` 写在路由表里，**新增路由时顺手就标了**，不存在忘记的第二处。所以本书 12.3 和 12.8 统一用 `meta.requiresAuth`。

### 陷阱 4：登录后 token 存了但请求没带上

```js
// ❌ 错误：登录页存了 token，但请求拦截器没有附加请求头
// src/api/index.js
service.interceptors.request.use((config) => {
  return config   // 没有附加 Authorization → 后端永远认为你"未登录"
})
```

```js
// ✅ 正确：请求拦截器里统一附加 token
import { useUserStore } from '@/stores/user'

service.interceptors.request.use((config) => {
  const userStore = useUserStore()
  if (userStore.token) {
    config.headers.Authorization = `Bearer ${userStore.token}`
  }
  return config
})
```

```js
// ✅ 配合：login action 里把 token 存进 Pinia
// src/stores/user.js
async function login(form) {
  const res = await loginApi(form)
  token.value = res.data.token       // ① 存进 Pinia（ref）
  localStorage.setItem('token', res.data.token)  // ② 顺手持久化
}
```

**原因**：登录只是把 token 放进了仓库，但**发请求时没人把它取出来放进请求头**，后端收到的是"匿名请求"，自然返回 401。Axios 拦截器就是那个"统一放 token"的地方。

**排查要点**：
1. 检查 `api/index.js` 的请求拦截器里有没有写 `config.headers.Authorization`；
2. 检查 `login()` action 里有没有把 token 存到 `token.value`（Pinia 的 ref），以及刷新页面后 token 是否从 localStorage 恢复；
3. DevTools → Network → 随便点一个接口，看 Request Headers 里有没有 `Authorization: Bearer xxx`；
4. 后端返回 401 时，优先看请求头而不是怀疑后端——90% 是请求没带上 token；
5. 别忘了一个隐藏坑：在拦截器里 `useUserStore()` 也要求 Pinia 已安装（呼应陷阱 1）。

## 📝 二、即时练习

3 个练习由易到难：先给 store 加能力，再玩存储策略，最后处理并发问题。每个练习都附「需求拆解 → 参考骨架 → 验收清单」，照着做就行。

### 练习 1：新增 `getUserInfo` action

**需求拆解**：
1. 在 `stores/user.js` 里新增状态 `userInfo`（默认 `null`）；
2. 新增 action `getUserInfo`：调用 `GET /user/info`，把返回的用户昵称、头像等数据存进 `userInfo`；
3. 在 `login()` 成功后自动调用 `getUserInfo()`，保证一登录就有完整用户信息；
4. 在页面（如顶栏头像区）读取 `userInfo` 展示。

**参考实现骨架**：

```js
// src/stores/user.js
import { defineStore } from 'pinia'
import { ref } from 'vue'
import { loginApi, getUserInfoApi } from '@/api/user'

export const useUserStore = defineStore('user', () => {
  const token = ref(localStorage.getItem('token') || '')
  const userInfo = ref(null)              // ① 新增状态

  async function login(form) {
    const res = await loginApi(form)
    token.value = res.data.token
    localStorage.setItem('token', token.value)
    await getUserInfo()                   // ③ 登录成功后自动拉取
  }

  async function getUserInfo() {          // ② 新增 action
    const res = await getUserInfoApi()
    userInfo.value = res.data
    return res.data
  }

  return { token, userInfo, login, getUserInfo }
})
```

```vue
<!-- 顶栏头像区：读取 userInfo 展示 -->
<template>
  <div class="user-bar">
    <el-avatar :src="userStore.userInfo?.avatar" :size="32" />
    <span>{{ userStore.userInfo?.nickname || '未登录' }}</span>
  </div>
</template>

<script setup>
import { useUserStore } from '@/stores/user'
const userStore = useUserStore()
</script>
```

**验收清单**：

- [ ] `stores/user.js` 中新增了 `userInfo` 状态
- [ ] `getUserInfo` action 调用接口并把结果存入 `userInfo`
- [ ] 登录成功后自动调用了一次 `getUserInfo`
- [ ] 页面能展示昵称和头像；接口失败时登录流程不被阻断（`getUserInfo` 用 try/catch 包住）
- [ ] 刷新页面后，先恢复 token 再拉取 `userInfo`，头像昵称不丢失

### 练习 2："记住我"复选框

**需求拆解**：
1. `LoginView.vue` 的表单底部加一个 `el-checkbox`，用 `remember` 变量绑定；
2. 登录成功时判断：勾选 → token 存 `localStorage`（永久）；不勾选 → 存 `sessionStorage`（关浏览器就清）；
3. 页面初始化时按「先 localStorage、后 sessionStorage」的顺序恢复 token；
4. 登出时把两个 storage 都清掉，避免残留。

**参考实现骨架**：

```vue
<el-form-item>
  <el-checkbox v-model="remember">记住我</el-checkbox>
</el-form-item>
```

```js
// 登录提交
const remember = ref(true)

async function handleLogin() {
  await userStore.login(form)
  // 按勾选状态决定存哪里
  const storage = remember.value ? localStorage : sessionStorage
  storage.setItem('token', userStore.token)
}
```

```js
// 初始化：优先 localStorage，其次 sessionStorage
// src/stores/user.js
const savedToken =
  localStorage.getItem('token') || sessionStorage.getItem('token')
const token = ref(savedToken || '')
```

```js
// 登出：两个 storage 都清掉
function logout() {
  token.value = ''
  userInfo.value = null
  localStorage.removeItem('token')
  sessionStorage.removeItem('token')
}
```

**验收清单**：

- [ ] 勾选"记住我"登录后，关闭浏览器再打开，仍是登录态
- [ ] 不勾选登录后，关闭浏览器标签页再打开，需要重新登录
- [ ] 登录时写入的 storage 与勾选状态一致（DevTools 里能验证）
- [ ] 刷新页面不丢登录态
- [ ] 登出后两个 storage 都被清空，不会"退了又自动登录"

### 练习 3：401 防抖跳转

**需求拆解**：
1. 在响应拦截器的 401 分支里，用一个模块级变量 `isRedirecting` 标记"已经在跳登录页了"；
2. 已标记 → 直接 reject，不再弹提示、不再跳转（防抖核心）；
3. 第一次遇到 401 时：清掉本地 token、弹一次"请重新登录"、跳转 `/login` 并带上 `redirect` 参数；
4. 清理跳转标记的时机要想清楚（见验收清单第 4 条）。

**参考实现骨架**：

```js
// src/api/index.js
import { ElMessage } from 'element-plus'
import router from '@/router'

let isRedirecting = false   // 模块级标记：是否已经在跳登录页

service.interceptors.response.use(
  (res) => res,
  (error) => {
    if (error.response?.status === 401) {
      if (!isRedirecting) {
        isRedirecting = true
        ElMessage.error('登录已过期，请重新登录')

        // 清掉本地登录态
        localStorage.removeItem('token')
        sessionStorage.removeItem('token')

        // 记住当前页面，登录后跳回来
        const redirect = router.currentRoute.value.fullPath
        router.push('/login?redirect=' + encodeURIComponent(redirect))
      }
      // 不管是不是第一次，统一 reject，让调用方拿到错误
      return Promise.reject(error)
    }
    return Promise.reject(error)
  }
)
```

**验收清单**：

- [ ] 同时发 3 个请求都返回 401 时，只弹 1 次提示、只跳转 1 次登录页
- [ ] 跳转登录页时携带了 `redirect` 参数（URL 里能看到）
- [ ] 重新登录成功后能跳回来源页面
- [ ] 用户手动退出登录、或正常走登录流程时，`isRedirecting` 能正确重置（提示：可以在 `login` 成功后或路由守卫放行时把它置回 `false`；更简单粗暴的方案是刷新页面——模块变量自动清零）
- [ ] 非 401 错误（如 500、网络错误）不受这段逻辑影响

## 🚀 三、进阶挑战

**挑战 1：登录后回到来源页（redirect 参数）**

12.7 登录页已经接了 `redirect` 参数，但很多人登录成功只是 `router.push('/')`，把来源页丢了。请把它用起来：

```js
// 提示：登录成功后这样跳转
const route = useRoute()
const redirect = route.query.redirect
router.push(typeof redirect === 'string' ? redirect : '/')
```

验收：在 `/goods` 页面手动把 token 清掉触发 401 → 跳登录页 → 登录成功后自动回到 `/goods`，而不是首页。注意 `redirect` 可能是数组（`?redirect=a&redirect=b`），用 `typeof` 判断一下更稳。

**挑战 2：token 过期自动续期（refresh token）**

生产级项目里，token 过期不该直接踢人，而是用「双 token」方案：`accessToken`（短期）+ `refreshToken`（长期）。当接口返回 401 时，先用 refreshToken 调 `/auth/refresh` 换新 token，成功则重放原请求；失败才跳登录页。

提示：
- 在 401 分支里区分"token 过期"和"refreshToken 也失效"两种情况；
- 用「单个 Promise 共享」的技巧避免多个并发请求同时去刷新（和练习 3 的防抖思想一脉相承）；
- 刷新请求本身不能走拦截器，否则会递归。

验收：伪造一个过期的 token，验证页面能无感续期继续操作，用户完全感知不到被踢下线。

## 🧠 本节小结

- **四大陷阱一句话版**：Pinia 必须在 `app.use(createPinia())` 之后才可用；localStorage 只存字符串、对象要 `JSON.stringify/parse`；守卫白名单漏了 `/login` 会死循环；token 存了仓库还要请求拦截器塞进 `Authorization` 才真正生效
- **排查靠工具不靠猜**：报错看 `no active Pinia`；本地存储看 DevTools Application；请求有没有带 token 看 Network 的 Request Headers
- **练习 1 给 store 加能力**：`getUserInfo` action + `login()` 成功后自动拉取，接口失败用 try/catch 兜住不阻断登录
- **练习 2 玩存储策略**："记住我"勾选存 localStorage、不勾选存 sessionStorage，登出时两个都清
- **练习 3 防抖 401**：模块级 `isRedirecting` 标记保证并发 401 只弹一次提示、只跳一次登录页；重置时机可在登录成功或刷新页面时处理
- **进阶挑战**：redirect 参数记得 `typeof` 判字符串（避免数组陷阱）；生产级用 refresh token 双 token 续期，刷新请求不能走拦截器否则递归

## 🔥 冷知识 / 小灶

- **"401 防抖"是真实项目的标配**：token 过期的那一瞬间，页面上往往有 3~5 个接口在并发请求，如果没有防抖，会同时弹出 5 个"登录已过期"、跳 5 次登录页。一个模块级 `isRedirecting` 标记就能把"5 连击"压成"1 次"。

<details>
<summary>💡 深究一下：refresh token 双 token 续期是怎么工作的？</summary>

生产级登录常用"双 token"方案：

```text
access token（短命，如 2 小时）→ 正常请求用，过期就 401
refresh token（长命，如 7 天）→ 只用来换新的 access token
```

流程：请求 401 → 拦截器拦截（先不跳登录）→ 带 refresh token 调刷新接口 → 成功则换新 access token **重放原请求** → 失败才踢回登录页。关键坑：**刷新接口自己不能走请求拦截器**（否则 401 → 刷新 → 401 → 刷新……无限递归）。本节进阶挑战点到为止，能说清"为什么刷新请求不能走拦截器"就已经超过多数初级面试者。

</details>
