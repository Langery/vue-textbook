第十一章教你"怎么把功能写对、写稳"：11.1~11.2 是测试金字塔与 Vue Test Utils，11.3 写组件单元测试，11.4 上 Vitest 的 `describe / test / expect / mock`，11.5~11.6 教 Vue DevTools 调试与高频 Bug 排查，11.7 做错误边界。这一节把前面所有技能**打到一个真实的旧项目上**——给第 3 章章末实战做的「记账小账本」（P5）补上单元测试：把计算逻辑抽成可测的纯函数、用 Vitest 验证收支结余、用 Vue Test Utils 测组件交互、再用 DevTools 揪出一个故意埋的 Bug。这套流程就是大项目 **Campus2Hand** 第 12 章交付前的"测试基线"：购物车金额、表单校验、订单状态流转都值得这样测。

> 🎯 **类比一下：章末实战 ≈ 给旧车装"行车记录仪 + 自检系统"**
> P5 记账本是一辆能开的旧车（功能正常但没有任何自检）。这节要做的是：把"算钱"抽成独立传感器（纯函数）、装上自检仪（Vitest 单测）、在仪表盘验证按钮交互（组件测试）、最后用透视镜（DevTools）揪出故意埋的统计 Bug。**车还是那辆车，但从此"每次改完跑一遍自检"就知道哪里坏了**——这就是测试基线。

> 🧑 **小白**：为什么要先抽纯函数再测？直接测页面不行吗？
> 🤖 **Vue 君**：页面测试像"整车路测"——贵、慢、依赖环境和 DOM；纯函数测试像"测发动机单机"——输入输出可预测，毫秒级跑完。**把核心计算抽出来单独测，又快又准**，页面测试只补交互层。
> 👨🏫 **老湿**：**验收标准最后一条是灵魂**：要能讲清"为什么算钱逻辑抽成纯函数再测，而不是只测页面"——组件测试防"交互接错"，纯函数测试防"逻辑算错"。两类测试各防住一类问题，这才是测试工程的完整拼图。

**`src/lib/ledger.js`** —— 纯函数，不 import 任何 Vue 的东西：

```js
// 纯函数：不依赖 Vue、不碰 DOM、输入相同输出必相同
// 这正是"可测试"的前提——回顾 11.1

/** 累加指定方向的金额 */
export function sumBy(records, direction) {
  return records
    .filter((r) => r.direction === direction)
    .reduce((sum, r) => sum + r.amount, 0)
}

/** 总收入 */
export function totalIncome(records) {
  return sumBy(records, 'income')
}

/** 总支出 */
export function totalExpense(records) {
  return sumBy(records, 'expense')
}

/** 结余 = 收入 − 支出 */
export function balance(records) {
  return totalIncome(records) - totalExpense(records)
}

/** 新增一条流水，返回带新 id 的记录（id 由调用方给，函数保持纯粹） */
export function createRecord({ id, item, amount, direction }) {
  return { id, item: item.trim(), amount: Number(amount), direction }
}
```

> 💡 **为什么把逻辑抽出来？**
> 组件里的 `computed` 测起来很麻烦：要 mount、要等渲染、要查 DOM。而 `totalIncome(records)` 这种纯函数，**直接传数组、断言返回值**就行——快、稳、失败信息还准。
> **"把逻辑从 UI 里抽出来"是提升可测试性最有效的一招**，比任何测试技巧都管用。

**`src/lib/ledger.test.js`** —— 纯函数单测：

```js
import { describe, test, expect } from 'vitest'
import { totalIncome, totalExpense, balance, createRecord } from './ledger'

// 测试数据
const records = [
  { id: 1, item: '旧书', amount: 15, direction: 'income' },
  { id: 2, item: '台灯', amount: 20, direction: 'expense' },
  { id: 3, item: '教材', amount: 25, direction: 'income' }
]

describe('ledger 汇总逻辑', () => {
  test('空列表：收支结余都为 0', () => {
    expect(totalIncome([])).toBe(0)
    expect(totalExpense([])).toBe(0)
    expect(balance([])).toBe(0)
  })

  test('只有收入时：totalIncome 正确，balance 等于收入', () => {
    const onlyIncome = [records[0]]
    expect(totalIncome(onlyIncome)).toBe(15)
    expect(totalExpense(onlyIncome)).toBe(0)
    expect(balance(onlyIncome)).toBe(15)
  })

  test('多条记录按方向分别累加', () => {
    expect(totalIncome(records)).toBe(40)   // 15 + 25
    expect(totalExpense(records)).toBe(20)
    expect(balance(records)).toBe(20)       // 40 - 20
  })

  test('删除一条支出后，balance 随之变化', () => {
    const afterDelete = records.filter((r) => r.id !== 2)
    expect(totalExpense(afterDelete)).toBe(0)
    expect(balance(afterDelete)).toBe(40)
  })

  test('边界：负数金额会被计入（当前实现不做防御）', () => {
    const weird = [{ id: 9, item: 'x', amount: -10, direction: 'expense' }]
    expect(totalExpense(weird)).toBe(-10)
  })

  test('createRecord：去掉首尾空格并把金额转成数字', () => {
    const r = createRecord({ id: 5, item: '  吉他  ', amount: '180', direction: 'income' })
    expect(r.item).toBe('吉他')
    expect(r.amount).toBe(180)
    expect(typeof r.amount).toBe('number')
  })
})
```

**`src/App.vue`** —— 组件调用纯函数：

```vue
<script setup>
import { ref, reactive, computed } from 'vue'
import { totalIncome, totalExpense, balance, createRecord } from './lib/ledger'

const records = ref([
  { id: 1, item: '九成新《高等数学》', amount: 15, direction: 'income' },
  { id: 2, item: '购入二手台灯', amount: 20, direction: 'expense' }
])

let nextId = records.value.length

const form = reactive({ item: '', amount: '', direction: 'income' })

// ====== 汇总全部走纯函数，组件不自己算钱 ======
const income = computed(() => totalIncome(records.value))
const expense = computed(() => totalExpense(records.value))
const remain = computed(() => balance(records.value))

function addRecord() {
  if (!form.item.trim() || !(Number(form.amount) > 0)) return
  records.value.push(createRecord({
    id: ++nextId,
    item: form.item,
    amount: form.amount,
    direction: form.direction
  }))
  form.item = ''
  form.amount = ''
}

function removeRecord(id) {
  const idx = records.value.findIndex((r) => r.id === id)
  if (idx > -1) records.value.splice(idx, 1)
}
</script>

<template>
  <div class="ledger">
    <h2 class="title">💰 记账小账本</h2>

    <!-- 汇总卡片 -->

        <div class="label">总收入</div>
        <div class="value income">{{ income }}</div>
      </div>
      <div class="card">
        <div class="label">总支出</div>
        <div class="value expense">{{ expense }}</div>
      </div>
      <div class="card">
        <div class="label">结余</div>

      </select>
```

```js
import { describe, test, expect } from 'vitest'
import { mount } from '@vue/test-utils'
import App from './App.vue'

describe('记账本组件', () => {
```

**照着做完可以顺手验证的 5 个知识点**：

| 验证动作 | 观察到什么 | 对应小节 |
|---|---|---|
| 把 `totalExpense` 改成也累加 income | 测试**红**在"多条记录按方向分别累加"这一条，其余仍绿——**精准定位** | 11.4 测试 |
| 改 `expect(totalIncome(records)).toBe(40)` 为 `toBe(0)` | 先见红再改回绿，**确认测试真的在测** | 11.4 |
| 删掉 `createRecord` 里的 `.trim()` | 那个断言立刻失败 | 11.1 纯函数 |
| 把 `computed(() => totalIncome(...))` 改回手写累加 | 测试**全绿但没在测组件**——因为逻辑搬走了，组件没覆盖到 | 11.3 覆盖范围 |
| 在 `App.vue` 里去掉 `data-test` 属性 | 组件测试全找不到元素而失败——**属性名要和测试对得上** | 11.3 |

> 💬 **老师备注：这个成品里藏着一个"测试的盲区"**
> 看最后一条验证：你把组件里的逻辑换成手写累加，**测试依然全绿**——因为算钱逻辑已经被抽到 `ledger.js`，组件测试只测了"点按钮后列表变长"这种表层行为，**没有验证组件确实调用了纯函数**。
>
> 这不是测试写错了，而是**测试覆盖范围的必然边界**。想覆盖到"组件确实用了这个函数"，得再补一条：把 `ledger.js` 整个 mock 掉（`vi.mock`），断言组件调用了它——那是 11.4 的 mock 技巧。
>
> **记住这个感觉**：测试能保证"你测到的东西是对的"，但**保证不了你没测到的东西是对的**。覆盖率报告（11.4）就是用来提醒你"还有哪些没测到"的。

## 🔮 它在最后的大项目里长成什么

这一节的"记账本单测"，就是大项目 **Campus2Hand 校园二手集市**的**测试基线雏形**：购物车金额合计（加购/删除/折扣后算总价）、发布表单校验规则、订单状态流转（待支付 → 已支付 → 已发货）——这三块核心逻辑，第 12 章都会像 `ledger.js` 一样抽成纯函数/独立模块并配上测试。到综合项目收尾时，你改一个价格计算不会心惊胆战：跑一遍测试，绿了就是真没改坏。

> 🧊 **冷知识**：为什么"抽成纯函数"对测试这么关键？因为纯函数**无副作用、输入决定输出**——同一输入永远同一结果，测试才能写"确定性断言"。反过来，如果计算逻辑直接写在组件里，你测的是"组件 + DOM + 生命周期"的混合物，一处改版三处要改测试。所以测试友好的代码，不是"能跑的代码"，而是**"边界清晰、副作用最少"的代码**——这也是为什么 `ledger.js` 要把算钱从组件里搬出来。

这个流程模拟的是真实工作流：①**测试先红**——故意把 `totalExpense` 写成也累加 income，跑测试立刻看到"支出合计"的用例失败，证明测试确实能抓住逻辑错误（而不是摆设）；②**DevTools 定位**——开 `npm run dev`，用 Components 面板看"支出合计"的 computed 值来源，结合 11.6 的排查五步法找到根因；③**修复全绿**——改回正确逻辑，测试通过，证明修复有效。全程演示的是**"测试先于肉眼发现问题"**：如果只靠手动点页面，那个 Bug 可能在"看起来正常"的界面里潜伏很久，直到某个用户的账目对不上才暴露。
