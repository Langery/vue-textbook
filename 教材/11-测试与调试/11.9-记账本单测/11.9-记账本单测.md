
# 11.9 章末实战：记账本单测（P11）

> 章节：第 11 章 测试与调试
> 课时：1 课时
> 类型：章末实战 · 独立小项目 P11

---

第十一章教你"怎么把功能写对、写稳"：11.1~11.2 是测试金字塔与 Vue Test Utils，11.3 写组件单元测试，11.4 上 Vitest 的 `describe / test / expect / mock`，11.5~11.6 教 Vue DevTools 调试与高频 Bug 排查，11.7 做错误边界。这一节把前面所有技能**打到一个真实的旧项目上**——给第 3 章章末实战做的「记账小账本」（P5）补上单元测试：把计算逻辑抽成可测的纯函数、用 Vitest 验证收支结余、用 Vue Test Utils 测组件交互、再用 DevTools 揪出一个故意埋的 Bug。这套流程就是大项目 **Campus2Hand** 第 12 章交付前的"测试基线"：购物车金额、表单校验、订单状态流转都值得这样测。

> 🎯 **类比一下：章末实战 ≈ 给旧车装"行车记录仪 + 自检系统"**
> P5 记账本是一辆能开的旧车（功能正常但没有任何自检）。这节要做的是：把"算钱"抽成独立传感器（纯函数）、装上自检仪（Vitest 单测）、在仪表盘验证按钮交互（组件测试）、最后用透视镜（DevTools）揪出故意埋的统计 Bug。**车还是那辆车，但从此"每次改完跑一遍自检"就知道哪里坏了**——这就是测试基线。

> 🧑 **小白**：为什么要先抽纯函数再测？直接测页面不行吗？
> 🤖 **Vue 君**：页面测试像"整车路测"——贵、慢、依赖环境和 DOM；纯函数测试像"测发动机单机"——输入输出可预测，毫秒级跑完。**把核心计算抽出来单独测，又快又准**，页面测试只补交互层。
> 👨🏫 **老湿**：**验收标准最后一条是灵魂**：要能讲清"为什么算钱逻辑抽成纯函数再测，而不是只测页面"——组件测试防"交互接错"，纯函数测试防"逻辑算错"。两类测试各防住一类问题，这才是测试工程的完整拼图。

## 🎯 项目需求（一句话）

在"记账小账本"（3.13 的 P5 产物）基础上补一个测试工程：把收支计算抽成纯函数模块并写 Vitest 单测（收入 / 支出 / 结余 / 边界情况），用 Vue Test Utils 对记账组件做渲染与交互测试，最后用 Vue DevTools 定位并修掉一个故意埋下的统计 Bug——测试全部通过、能一键回归。

### ✅ 验收标准（能跑、能展示）

- [ ] `npm run test`（或 `vitest run`）能跑通，终端里至少看到 8 个用例全绿
- [ ] 记账本的"收入合计 / 支出合计 / 结余"被抽成纯函数（`ledger.js`），不依赖组件与 DOM
- [ ] 纯函数单测覆盖：正常流水、空列表、删除后的重新汇总
- [ ] 组件测试用 `mount` 挂载记账组件，断言初始渲染、输入后点"记账"按钮能新增一条流水
- [ ] 用一个"故意埋的 Bug"（如支出统计把收入也算进去了），先在测试里看到它挂掉，再用 DevTools 定位修复，修复后测试全绿
- [ ] 能向同学讲清：为什么"算钱"的逻辑要抽成纯函数再测，而不是只测页面？组件测试和纯函数测试各防住什么问题？

## 🛠 分步提示（3~5 步，含关键代码锚点）

> 以下只给路线和关键锚点，**不贴全量答案**。卡住时回头翻 11.2 / 11.3 / 11.4 / 11.5 / 11.6 对应小节。

### Step 1：把 P5 项目复制出来 + 装测试依赖（回顾 11.1 / 11.2）

把你在 3.13 写好的记账小账本复制为本次实战项目（或直接在新 Vite 项目里重写迷你版）。安装测试依赖并加脚本：

```bash
npm i -D vitest @vue/test-utils jsdom
# package.json scripts 增加: "test": "vitest run"
```

在 `vite.config.js` 里补上测试环境配置（`test.environment = 'jsdom'`，参考 11.2 课堂配置），先跑一次空测试确认链路通。

### Step 2：把"算钱"抽成纯函数（回顾 11.1 的可测试设计）

新建 `src/lib/ledger.js`，把记账本里所有计算逻辑搬进去，做成不依赖 Vue 的纯函数：

```js
// src/lib/ledger.js
export function totalIncome(records) { /* 累加 direction === 'income' 的 amount */ }
export function totalExpense(records) { /* 累加 direction === 'expense' 的 amount */ }
export function balance(records) { return totalIncome(records) - totalExpense(records) }
```

> 锚点检查：组件里不再直接手算汇总，而是 `computed(() => balance(records.value))`——改一个函数，全项目（包括测试）同步生效。

### Step 3：写纯函数单测（回顾 11.4）

新建 `src/lib/ledger.test.js`，用 `describe / test / expect` 覆盖关键路径：

```js
import { describe, test, expect } from 'vitest'
import { totalIncome, totalExpense, balance } from './ledger'

describe('ledger 汇总逻辑', () => {
  test('空列表收支结余都为 0', () => { ... })
  test('只有收入时 totalIncome 正确、balance 等于收入', () => { ... })
  test('删除一条支出后 balance 随之变化', () => { ... })
})
```

锚点检查：刻意先写一个"错误期望"（比如期望 0）跑一次，确认测试真的会红；改回正确期望后全绿——先见红再见绿，才是有效测试。

### Step 4：组件测试（回顾 11.3）

新建 `src/App.test.js`（或组件同名测试）：用 `mount` 挂载记账组件，断言初始渲染出汇总卡片与空列表提示；找到输入框 `setValue('卖旧书')`、金额 `setValue('15')`、选方向后点击"记账"按钮，断言列表里新增了这一行、汇总数字更新。注意用 `nextTick` / `await` 等待 DOM 更新（11.3 教的异步断言姿势）。

### Step 5：埋 Bug → DevTools 揪出来（回顾 11.5 / 11.6）

在 `ledger.js` 里**故意**把 `totalExpense` 写成也累加 income（模拟"统计逻辑写反"），跑测试看它挂在哪几个用例；再开 `npm run dev`，用 Vue DevTools 的 Components 面板观察"支出合计"的 computed 值来源，结合 11.6 的排查思路找到根因、修复、重跑测试全绿。这一步请向同学演示：**测试如何先于肉眼发现问题**。

## 🔮 它在最后的大项目里长成什么

这一节的"记账本单测"，就是大项目 **Campus2Hand 校园二手集市**的**测试基线雏形**：购物车金额合计（加购/删除/折扣后算总价）、发布表单校验规则、订单状态流转（待支付 → 已支付 → 已发货）——这三块核心逻辑，第 12 章都会像 `ledger.js` 一样抽成纯函数/独立模块并配上测试。到综合项目收尾时，你改一个价格计算不会心惊胆战：跑一遍测试，绿了就是真没改坏。

> 🧊 **冷知识**：为什么"抽成纯函数"对测试这么关键？因为纯函数**无副作用、输入决定输出**——同一输入永远同一结果，测试才能写"确定性断言"。反过来，如果计算逻辑直接写在组件里，你测的是"组件 + DOM + 生命周期"的混合物，一处改版三处要改测试。所以测试友好的代码，不是"能跑的代码"，而是**"边界清晰、副作用最少"的代码**——这也是为什么 `ledger.js` 要把算钱从组件里搬出来。

<details><summary>🔍 想深究再看：为什么"故意埋 Bug → 测试先红 → DevTools 定位 → 修复全绿"是这套实战的精髓？</summary>

这个流程模拟的是真实工作流：①**测试先红**——故意把 `totalExpense` 写成也累加 income，跑测试立刻看到"支出合计"的用例失败，证明测试确实能抓住逻辑错误（而不是摆设）；②**DevTools 定位**——开 `npm run dev`，用 Components 面板看"支出合计"的 computed 值来源，结合 11.6 的排查五步法找到根因；③**修复全绿**——改回正确逻辑，测试通过，证明修复有效。全程演示的是**"测试先于肉眼发现问题"**：如果只靠手动点页面，那个 Bug 可能在"看起来正常"的界面里潜伏很久，直到某个用户的账目对不上才暴露。
