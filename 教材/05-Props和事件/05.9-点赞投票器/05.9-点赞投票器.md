
# 5.9 章末实战：点赞投票器（P4）

> 章节：第 5 章 Props 和事件
> 课时：1 课时
> 类型：章末实战 · 独立小项目 P4

---

第五章解决了组件间"怎么说话"的问题：数据从父到子靠 **Props**，子通知父靠 **emit**，双向绑定靠 **v-model**。这一节把它们拼成一个**能用的互动组件**——「点赞投票器」。设想校园二手集市里每件商品都有一排"👍 有用 / 👎 不推荐 / ⭐ 收藏"，这正是大项目 Campus2Hand 商品详情页「收藏 / 留言」交互组件与表单控件双向绑定的模型，先把单条交互做熟。

> 🎯 **类比一下：章末实战 ≈ 组装乐高**
> 前面 5.1~5.7 是散装零件（props、emit、v-model），这一节把它们拼成一辆能跑的小车。拼的时候你会发现：每个零件只干一件事，接口对了，整辆车就能转起来。

> 🧑 **小白**：我 Step 2 写完了，为什么点按钮数字不动？
> 🤖 **Vue 君**：八成是子组件直接改了 props——回去看 5.3，子组件只能 emit，让父组件改。
> 👨🏫 **老湿**：卡住别硬啃，回头翻锚点对应的小节。实战的价值不在"一次写对"，而在"知道卡住时去哪查"。

## 🎯 项目需求（一句话）

做一个"商品口碑投票器"：一条商品信息旁边有 👍 / 👎 两个按钮和一个 ⭐ 收藏开关——点赞数、点踩数、收藏状态都实时反馈在界面上——全程只用第 5 章已学的 props 传值、emit 事件、v-model，不引入任何新库。

### ✅ 验收标准（能跑、能展示）

- [ ] 项目能 `npm run dev` 启动，能看到一条或多条商品及其投票区域
- [ ] 商品的标题、初始票数通过 **props** 从父组件传入，子组件不私自改 props（回顾 5.3 只读性）
- [ ] 点 👍 会触发子组件 **emit** 事件，父组件更新票数，界面上数字 +1
- [ ] 同一用户不能无限刷票：同一件商品点赞后再次点击可"取消赞"（或已赞状态置灰）
- [ ] 收藏按钮用 **v-model** 双向绑定实现（父组件持有收藏状态，子组件通过 `defineModel` 同步）
- [ ] 展示页里至少复用同一个投票组件 3 次，各条数据互不影响

## 🛠 分步提示（3~5 步，含关键代码锚点）

> 以下只给路线和关键锚点，**不贴全量答案**。卡住时回头翻 5.1 / 5.5 / 5.6 / 5.7 对应小节。

### Step 1：定义好"一条商品"的数据结构

在父组件准备本地数据，字段固定为 `id / title / price / likes / dislikes`，另外维护每件商品的"我的态度"（未投 / 赞 / 踩）与"是否收藏"，方便做防刷票和收藏回显。

### Step 2：写子组件 `VotePanel`——props 只读 + emit 上报（回顾 5.1 / 5.6）

```vue
<script setup>
const props = defineProps({
  id: Number,
  title: String,
  likes: Number,
  dislikes: Number
})
const emit = defineEmits(['vote', 'collect'])
</script>
<template>
  <div class="vote-panel">
    <h4>{{ title }}</h4>
    <button @click="emit('vote', { id, type: 'like' })">👍 {{ likes }}</button>
    <button @click="emit('vote', { id, type: 'dislike' })">👎 {{ dislikes }}</button>
    <!-- 收藏按钮用 v-model 语法糖，见 Step 4 -->
  </div>
</template>
```

> 锚点检查：组件内部**绝不**写 `props.likes++`（只读，回顾 5.3）——所有改动都通过 emit 请父组件完成，父子各管一摊。

### Step 3：父组件接住事件、统一改状态（回顾 5.6 传参）

父组件写一个 `handleVote(payload)`，`payload` 里带着 `id` 和 `type`。用最朴素的写法：先按 `id` 找到对应商品，再修改它的 `likes / dislikes`（对象字段的直接增减在这一步是可行的，更讲究的"不可变更新姿势"到第 3 章再系统学）：

```js
function handleVote({ id, type }) {
  const target = goods.value.find((item) => item.id === id)
  if (!target) return
  if (myAttitude.value[id] === type) {          // 取消赞/踩
    type === 'like' ? target.likes-- : target.dislikes--
    delete myAttitude.value[id]                 // 置回未投
  } else {
    if (myAttitude.value[id] === 'like') target.likes--
    if (myAttitude.value[id] === 'dislike') target.dislikes--
    type === 'like' ? target.likes++ : target.dislikes++
    myAttitude.value[id] = type                 // 记录当前态度
  }
}
```

> 锚点检查：父组件 `goods` 用 `ref` 声明，模板里 `@vote="handleVote"` 绑定后，点按钮数字能正确增/减——事件链路（子 → 父）就通了。

### Step 4：收藏按钮换成 v-model（回顾 5.7）

把收藏单独抽成小组件 `FavoriteStar`，内部用 `defineModel` 暴露一个布尔状态，自身只管"点击取反"：

```vue
<script setup>
const collected = defineModel('collected', { type: Boolean, default: false })
</script>
<template>
  <button :class="{ collected }" @click="collected = !collected">⭐ 收藏</button>
</template>
```

父组件使用：`<FavoriteStar v-model:collected="favorites[id]" />`——父组件只维护 `favorites` 状态，子组件点一下，父组件数据自动同步。

### Step 5：加一点"真实感"的界面

标题显示"口碑得分"、切换商品、已收藏的按钮高亮……把投票组件复用 3 次以上，每条数据独立验证。想一想：为什么这条链路上，props 向下、emit 向上、v-model 双向，各自只干自己那一件事？

> 🧊 **冷知识**："同一用户不能无限刷票"用的是**态度记录（myAttitude）**，本质是"单一数据源"思想：`goods` 管票数、`myAttitude` 管我的态度、`favorites` 管收藏，三份状态各管一摊，互不越界。这个思路在真实项目中会演变成"状态管理"——Vue 生态里的 Pinia 就是把它做成了标准库。

<details><summary>🔍 想深究再看：为什么"取消赞"要记录 `myAttitude.value[id] === type`？</summary>

防刷票最朴素的实现是"幂等切换"：如果当前态度就是刚点的类型，说明是第二次点击（取消），票数 -1 并清空态度；否则是首次点击或切换态度，先回滚旧态度、再加新票。这里 `myAttitude` 是"以商品 id 为键、态度为值"的对象，天然支持多条商品各自独立——这也是用对象而不是数组存"每个商品一个态度"的原因：O(1) 查找、按 id 索引。第 3 章学"不可变更新"后，你还能把这里的直接增减改成更纯的函数式写法。

```vue
<script setup>
import { computed, ref } from 'vue'
import GoodsCard from './components/GoodsCard.vue'

// ====== 商品数据：父组件持有唯一一份，子组件只读不改 ======
const goods = ref([
  { id: 1, title: '九成新《高等数学》上下册', price: 15, likes: 12, dislikes: 1 },
  { id: 2, title: '降噪蓝牙耳机（小米）', price: 120, likes: 8, dislikes: 4 },
  { id: 3, title: 'Switch 续航版（含卡带）', price: 850, likes: 30, dislikes: 2 }
])

// ====== 我的态度：id -> 'like' | 'dislike'，用来防刷票 ======
// 键不存在 = 还没投过票（所以取消投票时用 delete，而不是存空字符串）
const myAttitude = ref({})

// ====== 收藏：id -> boolean，用 v-model 直接双向绑 ======
const favorites = ref({})
// 每件商品先给一个"未收藏"的初值，免得 v-model 拿到 undefined
goods.value.forEach((g) => {
  favorites.value[g.id] = false
})

// ====== 父组件统一记账：子组件只 emit 意图，改数据都在这里 ======
function handleVote({ id, type }) {
  const target = goods.value.find((item) => item.id === id)
  if (!target) return

  const prev = myAttitude.value[id]

  if (prev === type) {
    // 再点一次同一个 = 取消这一票
    if (type === 'like') target.likes--
    else target.dislikes--
    delete myAttitude.value[id]
    return
  }

  // 改主意：先把旧的那一票撤掉，再投新的一票
  if (prev === 'like') target.likes--
  if (prev === 'dislike') target.dislikes--
  if (type === 'like') target.likes++
  else target.dislikes++
  myAttitude.value[id] = type
}

// ====== 派生数据用 computed：它会跟着源数据自动重算 ======
const collectedCount = computed(
  () => Object.values(favorites.value).filter(Boolean).length
)
</script>

<template>
  <div class="page">
    <header class="page-head">
      <h2 class="title">👍 商品口碑投票器</h2>
      <p class="subtitle">props 传值 · emit 上报 · v-model 双向绑定</p>
    </header>

    <section class="list">
      <!--
        v-model 绑在「成员表达式」上。编译器会把它展开成：
          :modelValue="favorites[item.id]"
          @update:modelValue="favorites[item.id] = $event"
        也就是「props 往下传 + 事件往上传」，没有魔法
      -->
      <GoodsCard
        v-for="item in goods"
        :key="item.id"
        v-model="favorites[item.id]"
        :id="item.id"
        :title="item.title"
        :price="item.price"
        :likes="item.likes"
        :dislikes="item.dislikes"
```

**照着做完可以顺手验证的 7 个知识点**：

| 验证动作 | 观察到什么 | 对应小节 |
|---|---|---|
| 把 `GoodsCard.vue` 里的 `v-model="favorites[item.id]"` 改成 `:model-value="favorites[item.id]"`（只传不收） | ⭐ 按钮在**自己那一层**还是会变色，但父组件的 `favorites` 永远不变——单向绑定收不到子组件的更新 | 5.7 v-model 本质 |
| 把 `defineModel()` 换成手写的老两行：`defineProps({ modelValue: Boolean })` + `defineEmits(['update:modelValue'])`，再手动 emit | 行为完全一样——`defineModel` 只是把这两行包装成"读得到、写得出"的 ref | 5.7 defineModel |
| 在 `GoodsCard.vue` 里直接写 `props.likes++` | 控制台报 "Set operation on key ... failed: target is readonly"，数字纹丝不动 | 5.3 props 只读 |
| 连点两次 👍 | 数字先 +1 再 -1 回到 12，按钮的 active 高亮也消失了——"再点一次 = 取消"由 `myAttitude` 决定 | 5.6 事件传参 |
| 先点 👍 再点 👎 | 👍 变回 12、👎 变成 2，两种态度互斥——切换态度时旧的那票要先撤掉 | 5.6 事件传参 |
| 给第 2 件商品点 ⭐ | 只有第 2 件变黄，第 1、3 件纹丝不动——`v-model` 绑的是 `favorites[item.id]`，按 id 隔离 | 5.7 v-model 参数 |
| 把 `favorites` 的初值初始化那三行删掉，再点 ⭐ | 依然能正常收藏——因为 `defineModel` 的 `default: false` 会在你**第一次点之前**托底；但删掉初始化后，父组件里那个键的初始值是 `undefined` 而不是 `false` | 5.7 defineModel default |

<details>
<summary>💬 老师备注：这个成品里有三处"故意的非标准写法"，值得你找出来</summary>

**① `v-model` 绑在了成员表达式上，而不是一个普通变量。**
模板里写的是 `v-model="favorites[item.id]"`。很多人以为 `v-model` 只能写 `v-model="xxx"`，其实**只要右边是一个"可写的表达式"，编译器就能把它拆成两条指令**：

```
:model-value="favorites[item.id]"
@update:model-value="favorites[item.id] = $event"
```

所以 `v-model` 的本质从头到尾只有一句话：**props 往下传 + 一个 `update:modelValue` 事件往上传**。你在 Vue DevTools 里把组件的 props 展开，看到的就是这个 `modelValue`。

⚠️ 但这里有条硬限制：`v-model` **不能**直接绑在 `v-for` 的循环变量上（`v-model="item"` 会被编译器直接报错：*"v-model cannot be used on v-for scope variables because they are not writable"*）。原因很直白——`item` 只是循环的一个临时副本，改它不会写回数组。所以我们才需要 `favorites` 这个"按 id 存状态"的字典：**这才是这个设计真正的理由**，不是为了让代码看起来高级。

**② `myAttitude` 用"键不存在"来表示"没投过票"，而不是存一个空字符串。**
如果你写成 `myAttitude.value[id] = ''`，代码照样能跑，但你会多出一个"空字符串"这个第三种状态，`prev === type` 的判断就得多写一个分支。我们选择"**没有这个键 = 没投过**"，状态少一个，逻辑分支就少一个。

顺带一个 Vue 3 的小福利：`delete myAttitude.value[id]` 在 Vue 3 里**能触发更新**（底层是 Proxy，删除属性被拦截了）。在 Vue 2 里必须用 `Vue.delete()`，直接 `delete` 不会更新视图——老代码里那些 `Vue.set` / `Vue.delete` 的丑陋补丁，在 Vue 3 里全部消失了。

**③ 收藏状态在 `GoodsCard` 和 `FavoriteStar` 之间"转发"了一层。**
`GoodsCard` 自己有 `defineModel()`，模板里又写了 `<FavoriteStar v-model="collected" />`。看起来是"把一个 model 传给另一个 model"，有点绕，但它演示了一件很实用的事：**`defineModel` 返回的 ref 可以像普通数据一样往下传**。

不过这里有个**必须知道的坑**（我实测过）：如果父组件只写了 `:model-value="favorites[item.id]"` 而**没有**配套的 `@update:model-value`，那么 `useModel` 内部会走 `hasVModel === false` 的分支——子组件自己会把值改掉（按钮变黄了），但**父组件的数据永远收不到这个变化**。所以 `defineModel` 看起来像"本地 state"，实际上**双向能力完全取决于父组件有没有接住那个事件**。这正是 5.7 反复强调"v-model 是语法糖、不是魔法"的最好例证。

最后留个思考题：如果这个投票器要支持"同一件商品只能赞或踩其一、但允许多人各自投"，`myAttitude` 这个"以商品 id 为键的字典"还能直接用吗？（提示：想想多用户场景下，"我的态度"这个数据的归属方变了没有。）
