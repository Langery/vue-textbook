第九章打通了"前端 ↔ 后端"：9.2~9.4 是 Axios 裸请求，9.5 教独立实例与拦截器，9.6 教错误分类与重试，9.7 教 `useRequest` 三态封装与 `AbortController` 取消。这一节把它们串成一个**看得到的网络请求应用**——「每日一言壁纸」：每次打开随机加载一句话 + 一张壁纸，点按钮换内容，加载中、失败、重试、取消全套体验都有。它和大项目 Campus2Hand 的关联是结构性的：大项目所有接口请求都走本章封装的 Axios（实例 + token 注入 + 401 处理 + 统一错误），本实战的"api 层 + 三态"就是那套结构的迷你版。

> 🎯 **类比一下：本章实战 ≈ 用"标准零件"组装一台小机器**
> 9.5 的实例 + 拦截器是"标准电源模块"，9.6 的错误分类重试是"保险丝"，9.7 的 useRequest 是"总控开关"。这台「每日一言壁纸」小机器，就是用标准零件拼出来的：你不在组件里裸写 axios，就像不自己拉电线——**所有请求走封装通道，才是大项目的正确姿势**。

## 🎯 项目需求（一句话）

做一个"每日一言壁纸"页面：进入页面自动请求两条公开接口——一句话（文本）与一张壁纸（图片），展示出来；按钮"换一言 / 换壁纸"各自重新请求；全程带 loading / 错误提示 / 可重试——API 调用必须经过自己封装的 `api` 层 + `useRequest`，不允许在组件里裸写 `axios.get`。

### ✅ 验收标准（能跑、能展示）

- [ ] 项目能 `npm run dev` 启动，页面能看到一句中文名言/语录 + 一张全屏壁纸
- [ ] 首次加载时展示 loading（转圈或占位图），数据返回后淡入正文
- [ ] 请求失败时显示错误文案与"重试"按钮，点重试能重新请求（用 9.6 的错误分类处理）
- [ ] 点"换一言"只换句子不重新拉壁纸，点"换壁纸"只换图不换句子
- [ ] 组件里找不到裸 `axios.get`——所有请求都从 `api/` 模块导入，页面只用 `useRequest` 的结果
- [ ] 能向同学讲清：token 注入和统一错误提示为什么放在拦截器而不是每个组件里？"换壁纸"连续快速点击时怎么防止旧请求覆盖新结果？

## 🛠 分步提示（3~5 步，含关键代码锚点）

> 以下只给路线和关键锚点，**不贴全量答案**。卡住时回头翻 9.5 / 9.6 / 9.7 对应小节。

### Step 1：建 api 层：实例 + 拦截器（回顾 9.5）

新建 `src/api/http.js`：`axios.create({ timeout: 8000 })` 建独立实例（两个公开接口不同源，**不要写死 baseURL**）；请求拦截器里从 `localStorage` 取 fake token 注入 `Authorization` 头；响应拦截器把"非 2xx 的响应"统一 reject 并弹一句错误提示。再从该实例导出默认 `http`。

### Step 2：写接口模块（回顾 9.2 / 9.5 的模块化）

新建 `src/api/quote.js` 与 `src/api/wallpaper.js`，各导出一个返回 Promise 的函数：

```js
// api/quote.js
import http from './http'
export function getQuote() {
  return http.get('https://v1.hitokoto.cn/')   // 中文一言接口
}
```

壁纸接口可用 `https://picsum.photos/seed/{随机种子}/1600/900`——它直接返回图片，页面里用 `<img :src>` 引用即可（要"换一张"只需换 seed）。

### Step 3：页面用 `useRequest` 接三态（回顾 9.7）

复用课堂的 `useRequest(fetcher)`：内部维护 `data / loading / error` 并执行 `fetcher`。组件里：

```js
const { data: quote, loading: quoteLoading, error: quoteError, run: loadQuote } = useRequest(getQuote)
const { data: imgSeed, loading: imgLoading, error: imgError, run: loadImg } = useRequest(() => randomSeed())
```

`onMounted` 时同时 `loadQuote()` 与 `loadImg()`；模板按 `loading / error / data` 三态渲染：loading 显占位、error 显"加载失败 + 重试按钮（`@click="loadQuote()"`）"、成功显正文。

### Step 4：换一言 / 换壁纸 + 防连点

"换一言"按钮 `@click="loadQuote()"`——成功就更新 `data`，`useRequest` 内部自动把 `loading` 开关一遍。按钮在 `loading` 时禁用（回顾 9.6 防重复请求的思路），文案可换成"加载中…"。

### Step 5：取消请求与竞态（回顾 9.7）

给 `useRequest` 集成 `AbortController`：每次 `run()` 前先 `abort()` 上一个请求，`onUnmounted` 时也 `abort()`。锚点检查：快速连点"换一言"5 次，只应看到最后一次的结果；切走页面后 Network 面板里不再有"在飞"的请求。

**`src/api/http.js`** —— 本实战最该抄走的文件：实例 + 拦截器 + 错误分类三件事都在这儿：

```js
import axios from 'axios'

// 把 Axios 抛出的原生 error 翻译成「业务能看懂」的错误对象。
// 组件永远不需要知道 err.response / err.code 这些 Axios 内部细节。
export class ApiError extends Error {
  constructor(message, { kind, status = 0, cause = null } = {}) {
    super(message)
    this.name = 'ApiError'
    // kind: network | timeout | cancel | server | client | business | unknown
    this.kind = kind
    this.status = status
    this.cause = cause
  }
}

export function isCancelError(err) {
  return (
    axios.isCancel(err) ||
    err?.name === 'CanceledError' ||
    err?.code === 'ERR_CANCELED' ||
    err?.canceled === true
  )
}

function classify(err) {
  // ① 被主动取消：不是错误，单独归一类（回顾 9.7）
  if (isCancelError(err)) {
    return new ApiError('请求已取消', { kind: 'cancel', cause: err })
  }

  // ② 超时：err.code 是 ECONNABORTED / ETIMEDOUT，且没有 response
  if (err.code === 'ECONNABORTED' || err.code === 'ETIMEDOUT') {
    return new ApiError('请求超时，请检查网络后重试', { kind: 'timeout', cause: err })
  }

  const res = err.response

  // ③ 拿到了响应：说明请求「到过服务器」
  if (res) {
    if (res.status >= 500) {
      return new ApiError('服务器开小差了（' + res.status + '），稍后重试', {
        kind: 'server',
        status: res.status,
        cause: err
      })
    }

    return new ApiError('请求被拒绝（' + res.status + '），请检查填写内容', {
      kind: 'client',
      status: res.status,
      cause: err
    })
  }

  // ④ 连响应都没有：断网 / DNS 失败 / 跨域被拦
  if (err.request) {
    return new ApiError('网络连接失败，请检查网络后重试', { kind: 'network', cause: err })
  }

  return new ApiError('请求失败：' + (err.message || '未知原因'), { kind: 'unknown', cause: err })
}

// HTTP 200 但业务失败（回顾 9.6 的「三层分类」第三层）
function classifyBusinessError(body, status) {
  return new ApiError(body.message || body.msg || '业务处理失败（code: ' + body.code + '）', {
    kind: 'business',
    status
  })
}

const http = axios.create({
  timeout: 8000
  // ⚠️ 故意不写 baseURL：本节两个接口来自不同域名（hitokoto.cn / picsum.photos），
  // 完整地址写在各自 api 模块里。真实项目后端同源时才需要 baseURL。
})

http.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('c2h_token')
    if (token) {
      config.headers = config.headers || {}
      config.headers.Authorization = 'Bearer ' + token
    }
    return config
  },
  (error) => Promise.reject(error)
)

http.interceptors.response.use(
  // 成功：直接把 response.data 交出去，调用方不用每次写 .data
  (response) => {
    const body = response.data

    // ⚠️ 这一段是「业务错误」关卡，很多人会漏：
    // HTTP 200 只说明「服务器没崩」，不代表「业务成功」。
    // 后端约定 { code: 0 } 为成功时，code !== 0 必须在这里拦下来，
    // 否则页面会把 { code: 1001, message: '接口限流了' } 当成正常数据渲染。
    // 用 hasOwnProperty 判断而不是直接读 body.code：blob、字符串、
    // 没带 code 字段的普通 JSON 都不该被牵连。
    if (
      body &&
      typeof body === 'object' &&
      !Array.isArray(body) &&
      Object.prototype.hasOwnProperty.call(body, 'code') &&
      body.code !== 0
    ) {
      throw classifyBusinessError(body, response.status)
    }

    return body
  },
  // 失败：统一分类后再抛出去
  (error) => Promise.reject(classify(error))
)

export default http
```

**`src/api/wallpaper.js`**：

```js
import http from './http'

// 壁纸接口：https://picsum.photos/seed/{seed}/800/450
// 同一个 seed 永远返回同一张图，所以「换一张」= 换 seed。
//
// ⚠️ 这里刻意用 responseType: 'blob' 把图片当二进制取回来，
// 再转成 objectURL 给 <img> 用。为什么不让浏览器自己请求 <img src>？
// 因为那样图片不经过 axios 实例 —— 拦截器、超时、错误提示全都失效，
// 而「所有请求走 api 层」正是本实战的验收标准之一。
export function getWallpaper(seed, signal) {
  const url = 'https://picsum.photos/seed/' + encodeURIComponent(seed) + '/800/450'

  return http
    .get(url, { signal, responseType: 'blob' })
    .then((blob) => URL.createObjectURL(blob))
}
```

**`src/composables/useRequest.js`** —— 回顾 9.7 的三态封装，这里多做了三件事（老师备注里会解释）：

```js
import { ref, onUnmounted } from 'vue'
import { isCancelError } from '@/api/http'

// useRequest(fetchFn, { immediate })
// 返回 data / loading / error / run，fetchFn 的最后一个参数固定是 signal。
//
// ⚠️ 与 9.7 课堂版的三个「故意不同」：
//   1. 失败后**不重新抛出** —— 组件里直接 run() 时，重抛会变成
//      Uncaught (in promise)，控制台一片红，而组件已经用 error 状态渲染了。
//   2. 多一个 runId 序号 —— abort 只是「尽力而为」，响应可能已经回来了；
//      序号保证「过期结果」既不写 data 也不关 loading。
//   3. finally 里判 currentId === runId —— 否则连点时，旧请求的 finally
//      会把新请求的 loading 提前关掉，按钮提前解锁。
export function useRequest(fetchFn, options = {}) {
  const { immediate = false } = options

  const data = ref(null)
  const loading = ref(false)
  const error = ref(null)

  let controller = null
  let runId = 0

  async function run(...args) {
    // 新请求发出前，先把上一次还没回来的掐掉
    controller?.abort()

    const currentId = ++runId
    const currentController = new AbortController()
    controller = currentController

    loading.value = true
    error.value = null

    try {
      const result = await fetchFn(...args, currentController.signal)

      if (currentId !== runId) return undefined

      data.value = result
      return result
    } catch (err) {
      if (isCancelError(err)) return undefined
      if (currentId !== runId) return undefined

      error.value = err
      return undefined
    } finally {
      if (currentId === runId) loading.value = false
    }
  }

  onUnmounted(() => {
    controller?.abort()
  })

  // ⚠️ immediate 必须在 onUnmounted 之后调用：这样 loading 在 setup 阶段
  // 就同步变成 true，首帧渲染走 loading 分支，而不会出现
  // 「data 还是 null、模板却已经在读 quote.text」的崩溃。
  if (immediate) run()

  return { data, loading, error, run }
}
```

**`src/composables/useDailyWallpaper.js`** —— 把两个请求组装成页面直接能用的状态：

```js
import { onUnmounted } from 'vue'
import { useRequest } from './useRequest'
import { getQuote } from '@/api/quote'
import { getWallpaper } from '@/api/wallpaper'

let seedSeq = 0

// 每次「换壁纸」换一个全新 seed，保证 picsum 返回的是另一张图
function nextSeed() {
  seedSeq += 1
  return 'quote-wall-' + Date.now() + '-' + seedSeq
}

export function useDailyWallpaper() {
  // 当前正在展示的 objectURL。⚠️ 必须自己 revoke：
  // objectURL 是手动分配的内存，不像普通字符串会被 GC 顺手回收。
  let currentUrl = null

  function releaseCurrent() {
    if (currentUrl) {
      URL.revokeObjectURL(currentUrl)
      currentUrl = null
    }
  }

  // fetchWallpaper 是 useRequest 的 fetchFn：signal 由 useRequest 追加在末尾
  async function fetchWallpaper(signal) {
    const url = await getWallpaper(nextSeed(), signal)
    // 只有真正拿到新图才释放旧图；失败/取消时继续用旧图，别把页面清空
    releaseCurrent()
    currentUrl = url
    return url
  }

  // immediate: true —— 首帧就是 loading 态，不用手写 onMounted
  const quoteReq = useRequest(getQuote, { immediate: true })
  const wallReq = useRequest(fetchWallpaper, { immediate: true })

  onUnmounted(() => {
    releaseCurrent()
  })

  // ⚠️ 这里必须用箭头函数包一层，不能把 run 直接丢给 @click。
  // 写成 @click="refreshQuote" 时，Vue 会把 MouseEvent 当成第一个实参
  // 传给 run(...args) → fetchFn(event, signal) → signal 位置被顶掉，
  // 取消能力直接失效。事件对象是「UI 细节」，不该流进数据层。
  function refreshQuote() {
    return quoteReq.run()
  }

  function refreshWallpaper() {
    return wallReq.run()
  }

  return {
    quote: quoteReq.data,
    quoteLoading: quoteReq.loading,
    quoteError: quoteReq.error,
    wallpaper: wallReq.data,
    wallLoading: wallReq.loading,
    wallError: wallReq.error,
    refreshQuote,
    refreshWallpaper
  }
}
```

<details>
<summary>💬 老师备注：这个成品里有四处"故意的非标准写法"，每一处都是真实项目会踩的坑</summary>

**① `http.js` 里为什么把错误"再包一层"成 `ApiError`，而不是把 Axios 的 error 直接抛给组件？**
因为 `err.response.status`、`err.code`、`err.config` 这些是 **Axios 的私有形状**。你一旦在组件里写 `err.response.status === 500`，就等于把全项目的请求层焊死在 Axios 上——将来换 fetch 封装、或为了 SSR 换别的库，几十个文件全得改。包一层之后，组件只认两样东西：`err.message`（给人看的）和 `err.kind`（给机器看的），换底层只改 `classify()` 一个函数。**这正是 9.5 说的"请求的生命周期管理权收归统一层"的具体兑现。**

顺带一个易错点：业务错误关卡用 `Object.prototype.hasOwnProperty.call(body, 'code')` 判断，而不是直接 `body.code !== 0`。因为壁纸接口返回的是 `Blob`、一言接口返回的是没有 `code` 的 JSON——直接读会把它们统统误判成"业务失败"，页面直接白屏。

**② `useRequest` 里为什么加了 `runId`？`abort()` 不是已经解决竞态了吗？**
`abort()` 是**尽力而为**，不是**保证**。三种情况它拦不住：① 响应已经在路上、正准备进 `.then()`，这时再 abort 已经晚了；② 服务端返回很快，abort 发出时响应早就进了 JS 事件队列；③ 某些代理/CDN 会无视客户端取消，响应照样回来。所以真正的防护是**序号**：每次 `run()` 自增 `runId`，`await` 之后先比对"我还是最新那次吗"，不是就直接丢弃——既不写 `data`，也不碰 `loading`。

最关键的是 **`finally` 里那句 `if (currentId === runId)`**。9.7 课堂版没有它，所以快速连点时会出现这个鬼画面：请求 A 发出 → 请求 B 发出并 abort 了 A → A 的 `catch` 里识别出"取消"直接 return → **但 `finally` 照样执行，把 `loading` 置回了 `false`** → 请求 B 还在飞，按钮却已经解锁了。于是用户能点出第三个请求，B 的结果被当成"旧结果"扔掉。这不是理论推演，是本实战的挂载测试真的复现出来的 bug。

**③ 为什么图片要用 `responseType: 'blob'` 绕一圈，而不是直接 `<img :src="url">`？**
最省事的写法当然是后者，但那有个致命问题：**图片请求根本不走 axios**，于是拦截器、超时、错误提示、取消统统失效——用户点了 100 次"换壁纸"，Network 里就是 100 个各自为政的请求，弱网时永远转圈且没有重试按钮，页面还会在卸载后继续下载。绕这一圈把图片当二进制取回来、再 `URL.createObjectURL`，代价是多一次内存拷贝，换来的是"**所有请求走同一条通道**"这个验收标准。

代价的另一面：**objectURL 必须手动 `revokeObjectURL`**。它不是普通字符串，是浏览器里一块真实分配的对象内存，不会被 GC 顺手收走。真实项目里频繁换图的页面（图片预览器、轮播图），忘了 revoke 就是稳定泄漏——切页面卡顿、手机上直接被系统杀进程。所以上面 `useDailyWallpaper` 里有 `releaseCurrent()`，它在"拿到新图之后"才释放旧图（顺序反了的话，新图还没显示旧图就没了）。

**④ `immediate: true` 为什么必须写在 `onUnmounted` 之后？**
顺序本身不影响功能，但影响**首帧是否崩**。`immediate` 在 `setup` 阶段同步执行 `run()`，于是 `loading` 在第一次渲染前就已经是 `true`，模板走 loading 分支，安全。可如果改成在 `onMounted` 里 `run()`（很多教程的写法），首帧 `loading` 还是 `false`、`data` 还是 `null`，而模板已经在读 `quote.text`——**页面直接抛 `Cannot read properties of null` 白屏**。这不是我编的，是本实战的挂载测试第一次跑就抓到的。

顺带说清**为什么 `useRequest` 失败时不重新抛出**（9.7 课堂版是 `throw err`）：`run()` 返回的是 Promise，如果在 `onMounted` 里直接 `run()` 却不 await，重抛的异常就变成了 `Uncaught (in promise)`——控制台一片红，但组件其实已经用 `error` 状态正常渲染了错误提示。**错误状态已经渲染出来了，再抛一次只是噪音。** 真正需要区分"成功/失败"的调用方，用返回值判断即可（本实战的 `fetchWallpaper` 就是靠 `if (url)` 判断有没有拿到新图）。

<details><summary>🔍 想深究再看：为什么实战反复强调"所有请求走 api 层、组件不碰 axios"？</summary>

因为大项目里"接口通道"会持续演进：今天后端地址是 `http://test.com`，明天上线要换 `https://prod.com`；今天 token 存 localStorage，明天改存 cookie；今天 401 只弹框，明天要自动跳登录并刷新 token。这些变化如果散落在每个组件里，就是几十个文件的连锁改动；收进 `api/http.js` 一个文件，通常只改几行。9.5~9.7 教的"实例 + 拦截器 + 三态"，本质是把**请求的生命周期管理权**从组件手里收归到统一层——组件永远只跟"业务数据"打交道，这是工程化最重要的分工。
