ref 包对象默认深层响应式，代价是每个嵌套属性都要包 Proxy。对象特别大、或只想管顶层时，`reactive` 是另一套 API——但它有三条硬边界：不能替代基本类型、解构即失效、替换对象就断链。本节把 reactive 的局限和 shallowReactive、markRaw 进阶用法一次理清。

## 🤔 一、reactive 的三大局限（复习 + 扩展）

### 局限 1：只能包对象

```js
const count = reactive(0)  // ❌ 无效，不会响应式
```

基本类型请用 `ref`。

### 局限 2：不能整体替换

```js
let state = reactive({ count: 0 })

// ❌ 整个换成新对象，响应式丢了
state = reactive({ count: 1 })

// ✅ 用 Object.assign 合并
Object.assign(state, { count: 1, name: 'new' })
```

`reactive` 返回的是原始对象的 Proxy。你把变量指向一个新对象，Proxy 没有换，但原来的引用断了。

### 局限 3：解构丢响应式

```js
const state = reactive({ a: 1, b: 2 })
const { a } = state  // ❌ a 是普通数字
a = 2                // 页面不变
```

解决：`toRefs(state)`（见 8.3）。

## 💡 二、readonly：创建只读响应式

有些场景下，你希望数据是响应式的（数据变了 UI 自动更新），但**不允许组件内部修改**它。这时用 `readonly`：

```vue
<script setup>
import { reactive, readonly } from 'vue'

const original = reactive({ count: 0, name: 'Vue' })
const copy = readonly(original)

function tryToChange() {
  // ⚠️ 开发模式下会报警告，但不会阻止执行
  copy.count++
  console.log(copy.count)      // 1（居然还是改了？）
  console.log(original.count)  // 1（原对象也变了）
}
</script>
```

> 💬 **老师备注**：`readonly` 的"只读"是**约定层面的**——Vue 会在开发模式下打印警告，但它不会真的阻止你修改。它更多是起到一个 **"此地无银"的提示作用**：给同事看代码时，别人一看 `readonly` 就知道这个数据不应该被改。真正阻止修改要用 `Object.freeze`。

### readonly 的典型用法：封装暴露

```js
// useCounter.js
import { reactive, readonly } from 'vue'

export function useCounter() {
  const state = reactive({ count: 0 })

  function increment() { state.count++ }
  function decrement() { state.count-- }

  // 只暴露只读版本 + 操作方法
  return {
    state: readonly(state),  // 外部只能读不能改
    increment,
    decrement
  }
}
```

外部用 `useCounter()` 只能通过 `increment` / `decrement` 修改 count，不能直接 `state.count = 100`。

## 🔬 三、shallowReactive：只追踪顶层属性

```js
import { shallowReactive } from 'vue'

const state = shallowReactive({
  user: { name: '张三', age: 20 },
  count: 0
})

// ✅ 触发更新：顶层属性替换
state.count = 1
state.user = { name: '李四', age: 25 }

// ❌ 不触发更新：深层属性修改
state.user.name = '王五'  // 页面不变
```

和 `shallowRef` 类似，`shallowReactive` 只追踪**顶层属性**的读写。深层嵌套的对象不参与响应式。

适用场景：你有一个大对象，只有第一层的几个属性需要响应式，深层的数据不会变化。

## 🛠 四、markRaw：标记永不代理

有些对象你**永远不希望被 Vue 代理**——比如第三方库的实例（地图、图表、编辑器）：

```js
import { markRaw, reactive } from 'vue'

// 假设这是一个第三方地图实例
const mapInstance = new SomeMapLibrary()

// 标记：这个对象永远不要被 Vue 代理
markRaw(mapInstance)

// 放进 reactive 里也不会被代理
const state = reactive({
  map: mapInstance  // map 是原始对象，不是 Proxy
})
```

好处：
- **性能**：避免 Vue 递归代理大对象
- **安全**：有些第三方库的对象被 Proxy 后会出 bug

### markRaw + shallowReactive 组合

```js
import { markRaw, shallowReactive } from 'vue'

const state = shallowReactive({
  chart: null
})

// 初始化图表
state.chart = markRaw(new ECharts(dom))  // 图表实例永不代理
```

## 🔍 五、检测响应式状态

Vue 提供了几个"检测" API，用于调试或条件判断：

```js
import { reactive, readonly, ref, isReactive, isReadonly, isProxy, isRef } from 'vue'

const obj = reactive({ a: 1 })
const ro = readonly({ a: 1 })
const r = ref(0)

isReactive(obj)   // true  — reactive 创建的
isReactive(r)     // false — ref 不是 reactive（虽然内部用了）
isReactive(ro)    // false — readonly 不算 reactive

isReadonly(obj)   // false
isReadonly(ro)    // true

isProxy(obj)      // true  — reactive / readonly / shallowReactive 都是 Proxy
isProxy(ro)       // true
isProxy(r)        // false — ref 不是 Proxy

isRef(obj)        // false
isRef(r)          // true
```

> 💬 **老师备注**：这些 API 平时写业务代码很少用到，但它们非常有用——写 composable 时可以根据传入的是 ref 还是 reactive 做不同处理；写单元测试时可以用它们验证返回值的响应式状态是否正确。

## ⚠️ 六、常见陷阱

### 陷阱 1：markRaw 之后放进 reactive 会被再次代理？

不会。`markRaw` 打上的标记是永久的，即使你把它放进一个新的 reactive 对象，Vue 也认识这个标记并跳过代理。

### 陷阱 2：readonly 不等于深拷贝

```js
const original = reactive({ nested: { val: 1 } })
const ro = readonly(original)

original.nested.val = 2
console.log(ro.nested.val)  // 2 — 改了！因为 readonly 不是深拷贝
```

`readonly` 返回的还是对原对象的引用，只是加了只读约束.

### 陷阱 3：shallowReactive + ref 组合

```js
const state = shallowReactive({
  count: ref(0)
})

// ⚠️ 与 reactive 不同：shallowReactive 不解包 ref
state.count        // RefImpl（ref 对象本身，不是 0！）
state.count.value  // 0（需要手动 .value）
```

为什么？`reactive` 做的是**深层转换**，会把嵌套的 ref 自动解包；而 `shallowReactive` 只代理顶层属性，**属性值原样存储与暴露**——ref 对象也就原样躺在那里，不会自动解开。

再提醒一个连带坑：如果直接写 `state.count = 1`，会把顶层属性替换成普通数字，**与原 ref 切断连接**——之后原 `count` 怎么变，`state.count` 都不会再同步，也不触发更新。想保持响应式同步，请改 `state.count.value`。

结论：「shallowReactive 对顶层 ref **不会**自动解包，这与 reactive 不同；使用时记得 `.value`，直接替换整个属性会切断与原 ref 的连接。」

## 🧠 本节小结

- **reactive 三局限**：装不了基本类型（用 ref）、解构即丢响应（用 toRefs 找回）、整体替换对象会断链
- **markRaw**：标记对象永久跳过代理，再放进 reactive 也不会被包装，适合第三方实例/大数据
- **shallowReactive 不解包 ref**：顶层 ref 属性原样存储，需手动 `.value`；直接替换属性会切断与原 ref 的连接
- **readonly 是浅冻结**：只防第一层被改，嵌套对象仍可变；它不是深拷贝
- **工具函数自查**：`isReactive`/`isRef`/`isProxy` 帮你判断对象到底处在哪层响应式状态
- **选型思路**：要顶层性能用 shallow 系，要省心深响应用 ref/reactive 默认行为
