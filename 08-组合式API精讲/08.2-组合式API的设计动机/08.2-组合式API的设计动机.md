## 🤔 一、痛点一：代码组织散乱

前面 8.1 已经点到了——同一个功能的代码散落在不同选项里。我们来看一个真实场景：

假设你写一个"用户列表"组件，包含三个功能：
- A：搜索过滤
- B：分页
- C：批量选择

在选项式 API 中，代码长这样（简化版）：

```vue
<script>
export default {
  data() {
    return {
      // A: 搜索
      searchKeyword: '',
      filteredUsers: [],
      // B: 分页
      currentPage: 1,
      pageSize: 10,
      totalPages: 1,
      // C: 批量选择
      selectedIds: [],
      isAllSelected: false
    }
  },
  methods: {
    // A: 搜索
    search() { /* ... */ },
    // B: 分页
    prevPage() { /* ... */ },
    nextPage() { /* ... */ },
    // C: 批量选择
    toggleSelect(id) { /* ... */ },
    selectAll() { /* ... */ }
  },
  watch: {
    // A: 搜索
    searchKeyword() { /* ... */ },
    // B: 分页
    currentPage() { /* ... */ }
  }
}
</script>
```

三个功能的数据、方法、监听全部混在一起。你要改"分页"功能，得在 `data`、`methods`、`watch` 三个区域来回跳。**这就是"横跳式阅读"。**

组合式 API 的解决方案：

```
<script setup>
// ===== A: 搜索功能 =====
const searchKeyword = ref('')
const filteredUsers = ref([])
function search() { /* ... */ }
watch(searchKeyword, () => { /* ... */ })

// ===== B: 分页功能 =====
const currentPage = ref(1)
const pageSize = ref(10)
const totalPages = ref(1)
function prevPage() { /* ... */ }
function nextPage() { /* ... */ }
watch(currentPage, () => { /* ... */ })

// ===== C: 批量选择 =====
const selectedIds = ref([])
const isAllSelected = ref(false)
function toggleSelect(id) { /* ... */ }
function selectAll() { /* ... */ }
</script>
```

同一功能的代码聚在一起，阅读路径大幅缩短。

## 💡 二、痛点二：逻辑复用困难

### 2.1 Vue 2 时代的 Mixin

在 Vue 2 中，如果你想复用一段逻辑（比如"鼠标位置追踪"），典型做法是用 **Mixin**（混入）：

```js
// mouseMixin.js
export const mouseMixin = {
  data() {
    return { x: 0, y: 0 }
  },
  mounted() {
    window.addEventListener('mousemove', this.update)
  },
  unmounted() {
    window.removeEventListener('mousemove', this.update)
  },
  methods: {
    update(e) {
      this.x = e.pageX
      this.y = e.pageY
    }
  }
}
```

```vue
<script>
import { mouseMixin } from './mouseMixin'
export default {
  mixins: [mouseMixin],  // 混入
  data() {
    return { x: 100 }    // ⚠️ 和 mixin 里的 x 冲突！
  }
}
</script>
```

Mixin 的三大问题：

| 问题 | 说明 |
|---|---|
| **命名冲突** | 多个 mixin 如果有同名属性/方法，后混入的覆盖前面的，你不知道谁盖了谁 |
| **来源不透明** | 用了这个 mixin 后，`this.x` 是组件自己的还是 mixin 带来的？不看 mixin 源码根本不知道 |
| **隐式耦合** | 一个 mixin 可能依赖另一个 mixin 的属性，或者依赖组件里某个 data，改起来提心吊胆 |

### 2.2 组合式 API 的 composable

组合式 API 的方案是把逻辑写成**普通 JS 函数**——称为 **composable**（组合式函数）：

```js
// useMouse.js
import { ref, onMounted, onUnmounted } from 'vue'

export function useMouse() {
  const x = ref(0)
  const y = ref(0)

  function update(e) {
    x.value = e.pageX
    y.value = e.pageY
  }

  onMounted(() => window.addEventListener('mousemove', update))
  onUnmounted(() => window.removeEventListener('mousemove', update))

  return { x, y }
}
```

```
<script setup>
import { useMouse } from './useMouse'

const { x, y } = useMouse()  // 一眼看到：x 和 y 来自 useMouse
</script>

<template>
  <p>鼠标位置：{{ x }}, {{ y }}</p>
</template>
```

对比 Mixin：

- ✅ **无命名冲突**：解构时如果冲突，IDE 直接报错
- ✅ **来源透明**：`const { x, y } = useMouse()`，一眼知道数据来源
- ✅ **无隐式耦合**：每个 composable 是独立函数，输入输出明确

## 🔬 三、痛点三：TypeScript 支持

这个对大专阶段不做硬性要求，但你了解一下：选项式 API 中 `this` 的类型推断一直是个难题，而组合式 API 中一切是普通函数，TypeScript 的类型推导天然完美。

```ts
// 选项式：this 类型需要额外声明
// 组合式：普通函数，TS 自动推导
function useCounter(initial: number) {
  const count = ref(initial)  // Ref<number>，自动推导
  return { count }
}
```

## 🛠 四、设计哲学："组合" > "继承"

组合式 API 的设计哲学来自一个经典编程原则：

> **组合优于继承（Composition over Inheritance）**

- **继承**（类似 Mixin）：把功能"混进"组件，你不知道混进了什么，也不知道什么时候会冲突
- **组合**（composable）：把功能封装成独立函数，组件需要什么就主动"引入"什么

打个比方：

- Mixin 像往汤里倒了一包"神秘调料"——味道变了，但你不知道里面有什么
- Composable 像往汤里加盐、加胡椒、加葱花——每样都看得见，多了少了你自己控制

## ⚠️ 五、常见误区

### 误区 1：「选项式 API 要被淘汰了」

不会。Vue 官方明确表示选项式 API 会长期保留。两种写法各有所长，小项目用选项式完全没问题。但如果你要做中大型项目、要写可复用逻辑，组合式 API 的优势会越来越明显。

### 误区 2：「组合式 API 就是不用 this 了」

"不用 this"只是表面好处。真正的核心是**逻辑组合与复用**。组合式 API 让你能把一段完整的功能（数据 + 方法 + 生命周期 + 监听）打包成一个函数，随处引用。

### 误区 3：「学了组合式就要忘掉选项式」

两种 API 共享同一套响应式系统，你理解 `ref` / `reactive` / `computed` / `watch` 的原理后，用哪种形式只是语法差异。

## 🧠 本节小结

- **动机一：代码组织**——相关逻辑在选项式里被 data/methods/watch 拆散，组合式让它们并排
- **动机二：逻辑复用**——选项式靠 mixin 混入（命名冲突、来源不明），组合式抽函数/composable 干净可控
- **动机三：类型友好**——组合式全是普通函数调用，TypeScript 推导更自然
- **误区提醒**：学了组合式不用"忘掉选项式"，两者共享响应式内核，读老项目仍需要选项式
- **`this` 不再是主角**：组合式用闭包变量传参取值，规避了 `this` 丢失与指向坑
